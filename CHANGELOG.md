# Changelog

## 3.0.3

- **The extension is now called PostgreSQL Query Booster:** The name change is a pure renaming for the Marketplace listing. The display name, the title of the activity bar container, the settings page and the category every command appears under in the Command Palette now read *PostgreSQL Query Booster* instead of *PostgreSQL Query Builder*, and the output channel of the same name was renamed with them. Nothing that is stored keeps the old label: command ids, view ids, every `postgresQueryBuilder.*` setting key and the workspace files `.vscode/postgres-query-builder.queries.json` and `.vscode/postgres-query-builder.mappings.json` are unchanged, so existing settings, keybindings, bookmarked queries and shared column mappings keep working without being touched.

    - **The changelog is now English throughout.** The entries for version 2.0.4 and older were written in German and are now translated, so that the release notes shown on the Marketplace read in one language from the first version to the last. Only the wording changed; no entry was added, removed or reordered.
    - **The extension carries an icon.** Until now it was listed with the grey placeholder square every extension without one gets, which made it hard to pick out in the extension list and in the activity bar. It now ships a 128×128 icon of its own.
    - **The README describes what the extension has become.** It still explained the state of version 0.2, named commands that have not been called that for a year and was silent about the join builder, the exports, the bookmarked queries, the modify history, the column mappings and the formatter. It now covers all of them, in the order in which you meet them.

- **A call whose arguments are tuples is now broken into tuples:** A `jsonb_build_object('p_mandt', co_mandt, 'p_counter', co_counter, …)` that grew past the wrapping threshold put every single argument on a line of its own, which tore each key away from its value and turned a compact object into a column of eighteen lines in which nothing showed what belonged together. Such a call now keeps its pairs side by side, so `'p_mandt', co_mandt,` reads as one entry. Which functions this applies to is a setting, `postgresQueryBuilder.format.argumentGroups`, so it never touches a function whose arguments are a plain list.

    - **The value describes the shape of the argument list.** It is a `+`-separated list of group sizes whose last entry repeats until the arguments run out: `"2"` for the key/value builders, `"1+2"` for a `DECODE` that keeps its subject on the first line and pairs the branches after it, `"1+1+2"` when the first two arguments each deserve a line. A remainder shorter than the repeating group — the `elsevalue` of a `DECODE`, or the odd argument of a `jsonb_build_object` that is missing one — gets a line of its own, where it is easy to spot.
    - **`json_build_object`, `jsonb_build_object` and `decode` are configured out of the box**, and a key may carry a schema (`oracle.decode`) to apply only to the qualified call. A bare name matches however the call is qualified, and a value of `"0"` switches a built-in entry off again. The setting is read from `.pgformat.json` under the key `argumentGroups` as well, so a repository can decide it for everyone working in it.
    - **A tuple that no longer fits on a line gives the grouping up.** As soon as one of the arguments is itself broken across lines — a nested `jsonb_build_object`, a `CASE`, a sub-select — the call falls back to one argument per line, because a pair whose second half runs over five lines hides the pairing instead of showing it. The nested call keeps its own grouping.

- **A line comment no longer ends on `*` or `/`:** A comment such as `-- rate = a/b/` or `-- see table*` looks harmless on its own, but its last character is one half of a block comment marker. As soon as that line sits next to another one — code commented out with `/* … */`, a statement pasted into a generated block, a comment reflowed onto the line above — the `/` and the `*` next to it form `*/` or `/*`, and the enclosing comment ends or begins in a place nobody wrote. The formatter now closes such a comment with a single space, so `-- see table*` becomes `-- see table* ` and the character next to it can never complete a marker.

    - **Only the affected comments change.** A comment that ends on any other character is left exactly as it is, so formatting a file does not fill it with trailing blanks. A `*` or `/` in the middle of a comment, a division in code and the `*/` that closes a block comment are untouched, and the space is added once no matter how often the file is formatted.

## 3.0.2

- **A relation can now be followed from the column header, taking the whole result along:** Right-clicking a cell opens the related table filtered to that one row's value, which answers a question about a single record but says nothing about the rest of the result. The context menu of a column header now offers the same relations — foreign keys, tables pointing back at this one, and custom mappings — as *Open ... joined with ...*. Instead of a filter it opens the related table with the current one joined in, so `SELECT rk_id, rk_rk FROM regionen WHERE rk_rk = 'DEB'` becomes a query on `sap_rk_zuordnungen` whose `ON` clause carries `rk_rk = 'DEB'` over. A mapping's extra conditions and every one of its additional column pairs join in as well, the sort order of the current query is kept, and only column names the two tables actually have are accepted.

    - **Neither table is given an alias while none is needed**, so the condition you wrote reads unchanged in its new place. Only when both tables share a column name would that condition become ambiguous; the two tables are then aliased the same way the JOIN builder aliases them, and the carried-over `WHERE` and `ORDER BY` clauses are qualified to match — string literals, casts, function names and already qualified references stay as they are.
    - **A query that is more than a plain `SELECT ... FROM one_table` is carried over whole.** A grouped query, a `UNION` or one that already joins cannot hand over its `WHERE` clause without changing meaning, so it is joined in as a sub-select instead. The relation can be followed from any result, not only from a simple one.

- **A `:name` placeholder marks a variable that *View Data* cannot guess:** The command recognises a PL/pgSQL variable by the position it stands in — next to a comparison, in an `IN` list, after `BETWEEN` or `LIMIT`. An identifier in the select list or as a function argument is indistinguishable from a plain column there, so a query pulled out of a procedure asked for `pi_persnr` in the `WHERE` clause but ran into `column "v_von" does not exist` for `SELECT v_von AS from_day` and `LEAST(v_bis, ...)`. Writing `:v_von` and `:v_bis` now settles it: a `:name` placeholder is always offered for substitution, wherever it stands, and is replaced together with its colon. A `::` cast and a `:=` assignment keep their meaning, and `a=:from` is read as the operator plus the placeholder rather than as one operator.

- **Duplicating a row no longer copies values the database fills in itself:** A duplicate was a literal copy of every column, so a table with a `serial` primary key produced a row whose key already existed and the commit failed on a unique violation; a `created_at DEFAULT now()` or a `created_by DEFAULT CURRENT_USER` quietly carried the source row's timestamp and user name into a record that was written today by someone else. A duplicate now leaves exactly those columns to the database: identity and generated columns, defaults built from a function call — `nextval()`, `now()`, `gen_random_uuid()` and your own functions such as `oracle.sysdate()` alike — and the context keywords `CURRENT_DATE`, `CURRENT_TIMESTAMP` and `CURRENT_USER`. Such a cell shows a dimmed `DEFAULT` instead of a copied value and names the responsible expression in its tooltip, and because the column is left out of the `INSERT` altogether, the database fills it on save.

    - **A constant default is still copied.** `DEFAULT 0`, `DEFAULT 'open'` or `DEFAULT 0::numeric(10,2)` describes a starting value, not a per-row value, so a status the source row was deliberately moved away from is not silently reset.
    - **Every cell can be decided individually.** The context menu of a duplicated cell offers *Copy Value From Source Row* to take the original value after all, and *Reset to Default* to hand a column back to the database. Typing into a cell replaces the marker; clearing it again restores it.
    - **A verbatim copy is one click away.** *Duplicate Row Exactly* in the row's context menu copies everything, generated values included, for the cases where the copy is the point.
    - **The setting `postgresQueryBuilder.duplicateRowResetDefaults`** decides what duplicating does by default: `volatile` as described above, `all` to reset every column that has a default, or `none` for the previous verbatim behaviour.

- **Editing a length-limited column shows how much room is left:** A `varchar(10)` accepted typing far beyond its limit and only complained once the value was left — you had to count characters yourself to know how close you were. While a cell is edited, a small counter now appears at its lower right corner and updates on every keystroke, and the same counter sits underneath the field in the Single Record View. It reads `42 / 100 · 58 left`, turns into a warning colour from four fifths of the length on and reports `105 / 100 · 5 over` once the value is too long, so the limit is visible before saving is blocked. Characters are counted the way the column counts them, so `ä`, `ß` and `€` each use one of them. Columns without a limit, such as `text` or a `varchar` without a length, show no counter at all.

- **Character limits are visible in Data Viewer headers:** A `varchar` column used to show only its base type, so the maximum length was hidden until an edit failed or the schema was checked elsewhere. Headers now show the declared length, such as `varchar(10)`, while other types keep their complete PostgreSQL type information.

## 3.0.1

- **A long text no longer has to be read through a grid cell:** A `text` column holding a whole letter, a log excerpt or a formatted JSON document was only visible through a one-line cell or, at best, a small box in the Single Record View — you could scroll it, but not read it comfortably, and editing meant typing into a field that showed three of its forty lines. Every cell can now be opened in a normal editor tab: the entry *Open Value in Editor* in the cell's context menu and the pencil button next to each field of the Single Record View hand the value to a tab with syntax highlighting, search, folding, multi-cursor and everything else the editor offers. Saving that tab writes the value straight back into the cell as a pending change — it appears in the grid like a typed edit, so *Preview SQL* and *Commit* treat it exactly the same, and nothing reaches the database until you commit. Closing the tab discards its scratch file; emptying it sets the cell to `NULL`.

    - **The tab speaks the language of the column.** A `json` or `jsonb` value opens as a `.json` file and an `xml` value as `.xml`, so the editor colours, folds and validates it, while everything else opens as plain text. The tab is named after the table and the column it came from, and the file lives in the extension's own storage — never next to your project.
    - **A value that cannot be written back says so.** A column of a result that has no writable source, a row already marked for deletion or a read-only view still opens for reading, but the status bar states up front that changes are not written back. If the data is reloaded while the tab is open, saving reports that the cell is no longer part of the result instead of silently editing a different row.

- **A button shows what it does instead of spelling it out:** Buttons had drifted between icon-with-label and label-only, so a row of actions was read as a wall of words and the icon — the part you actually recognise — was crowded out. The rule is now the other way round: a button carries its icon alone and names the action in full in its tooltip, and a written label is added only where the icon cannot carry the action on its own, such as the primary action of a dialog. `STYLEGUIDE.md` states this as the default for every new button, and the *Open in Editor* action of the Single Record View follows it as a plain pencil.

## 3.0.0

- **Every surface now looks like part of the same extension:** Each panel, dialog and sidebar had grown its own styling over time, so the same button could be a different size, a different shade and a different shape depending on where you met it, and colours such as a fixed green, orange, red or blue were baked in — they clashed with dark themes and became unreadable in high-contrast ones. All surfaces now draw from one shared stylesheet with a single set of design tokens for spacing, font sizes, corner radii, stacking order and colour roles, so a button, an input, a dialog and a badge look and behave the same everywhere. Nothing in the interface carries a fixed colour any more; every shade is derived from the active VS Code theme and therefore adapts automatically to light, dark and high-contrast.

    - **Buttons became small enough to stop dominating the toolbar.** The toolbar was filled with wide buttons whose long captions gave rarely used functions the same weight as the ones you press constantly. Every button now shows a compact icon with a short label and carries its full description in the tooltip — but **nothing was hidden**: every action that was reachable before is still visible, just smaller. The Data Viewer toolbar is additionally divided into groups (row editing, table settings and export, loading more rows) separated by thin rules, so the buttons that belong together read as a unit instead of one long row. In the query bar, the actions whose icon says it all — parameters, saving, formatting — are icon-only, while *Run* stays a labelled primary button.
    - **Row states are readable, not just colourful.** A modified, inserted, deleted or duplicated row used to be filled with a strong colour wash. It now gets a light tint mixed from the theme plus a coloured stripe on its row number, so the state is obvious at a glance, the cell content stays legible, and the difference between the states does not depend on distinguishing shades of a wash.
    - **Icons are drawn by the extension itself.** They ship as a small inline SVG sprite that follows the surrounding text colour, so no font, no network access and no relaxation of the webview's `default-src 'none'` content security policy was needed for them.
    - **The tree views speak the same language.** Tables now carry a table icon instead of a class symbol, and schemas, category folders and both saved-query groups have tooltips explaining what they contain and where their entries are stored.

- **The connection form is protected by a content security policy like every other view:** It was the one webview that was still loaded as a raw HTML file, which meant it ran without a CSP and without a script nonce — the protection every other panel already had. It is now built through the same shared document builder, so it gets the strict policy, the nonce and the shared design at once.

- **The design rules are written down instead of living in people's heads:** `STYLEGUIDE.md` describes for contributors and AI assistants how a surface is assembled, which tokens, button classes and layout blocks exist, and how a new icon is drawn. The document is kept honest by tests: a token, button modifier or template placeholder that is added, renamed or removed without updating the guide makes the test suite fail.

- **The extension speaks English everywhere, and the same action is called the same thing everywhere:** Without a connection, the *Tables* view and the *Search* sidebar both offered you a way to pick a connection or create one — but in two different languages, with two different wordings, and once with icons and once without, so it was not obvious that the two pairs of buttons did exactly the same thing. Both now read *Select Connection* and *New Connection*, in the same order, with the same meaning and with the same database and plus icon, and the connection badge in the Data Viewer uses that same wording instead of a third variant. The last German texts left over from the extension's early days are gone as well: the welcome text of the *Tables* view, the hints in the *Search* sidebar and in the mappings manager, and all formatter settings in the settings editor — over twenty descriptions that were still German — are now English. Tests scan the manifest and every source file for German text and for the shared connection labels and icons, so neither can drift apart again.

- **Saved queries are now called bookmarked queries:** The name never matched what you saw or what the feature does — you store a query with a star, the tree shows a bookmark, and a query you keep coming back to is a bookmark, not a document you saved. The view in the activity bar is now called *Bookmarked Queries*, the star in the query bar reads *Bookmark this query for reuse*, its dialog is *Bookmark Query* (or *Update Bookmarked Query* when you overwrite an existing one), and the commands in the palette and the context menus follow the same wording — *Run Bookmarked Query*, *Rename Bookmarked Query*, *Delete Bookmarked Query*, and so on. Only the wording changed: your stored queries, the workspace file that shares them, the setting that points at it and every keyboard shortcut or command binding keep working untouched. A test checks the manifest and all bookmark surfaces so no corner of the interface falls back to the old name.

- **A bookmark opens on a double click, just like a table:** Clicking a bookmarked query once already ran it and opened a Data Viewer tab, so simply selecting an entry — to rename it, move it or look at its parameters in the tooltip — fired off a query you never asked for. A single click now only selects; the query runs on the second click, exactly as the *Tables* view has always behaved. Running a bookmark from the context menu, the play icon or the command palette is unchanged and still takes one action.

- **You can see at a glance that the Data Viewer is working:** A running query only showed a small *Loading data…* line in the toolbar, so on a slow statement the grid just sat there with stale rows and it was easy to think nothing had happened. A large spinner now covers the rows while data is on its way. It deliberately stops at the pinned header: the column headers and the filter row stay uncovered and usable, so the next filter can already be typed while the current query is still running.

- **A cell's context menu stays usable on a heavily linked table:** Every foreign key pointing at a column adds an *Open Foreign Key* entry, so on a central table the menu grew into a scrolling list in which the one entry you wanted was impossible to spot. From ten entries on, the menu now opens with a search box in focus: typing narrows the list to the matching entries, Enter opens the first of them, Escape closes the menu. Shorter menus are unchanged and open without a search box.

- **Row number and row actions stay where you can reach them, and look like what they are:** Both columns are part of the grid but hold nothing you can edit — that was not visible, and on a wide table they scrolled out of sight, so you could no longer tell which row you were looking at or delete it without scrolling all the way back. They now carry a dimmed background that sets them apart from the editable cells and are frozen at the left edge: scrolling sideways moves only the data columns past them. The action column pins itself right behind the row numbers and follows their width as it grows from two to five digits.

- **Column widths can be adjusted:** Wide columns were cut off at a fixed width while narrow ones wasted space, and there was no way to change that. Every column header now has a drag handle on its right edge — pull it to make the column as wide or as narrow as the data needs. The width sticks to the column: it survives sorting, filtering, reloading and even moving the column to a different position, and the filter box shrinks along with it so a column can really be made narrow.

- **A third click on a column header brings the previous order back:** Clicking a header sorted ascending, clicking again descending, and a third click simply started over — there was no way to get rid of a sort. The header now cycles ascending, descending, off: the third click restores the order that was in place before that column was clicked, so having a quick look at one column no longer throws away the sorting you had set up.

- **Connections are managed in one place:** The Search sidebar carried buttons for selecting, opening and closing a connection, which had nothing to do with searching, and in the Tables view those actions disappeared as soon as a connection was active. The connection buttons are gone from Search; the Tables view now shows *Select Connection*, *New Connection* and *Disconnect* as icons in its title bar, permanently and regardless of whether a connection is currently open. The search field is now the first thing in the Search sidebar, so it is where you look for it.

## 2.2.3

- **Queries can be saved with placeholders and run from anywhere:** A query that took effort to write was gone as soon as the panel closed — the history helped only within the same panel, and a recurring query had to be re-typed with different values every time. The Data Viewer now has a *"☆ Save Query"* button that stores the statement under a name, and any `:name` written in the SQL becomes a placeholder that is asked for before the query runs. Saved queries live in a *"Saved Queries"* view in the activity bar and are reachable independently of any table: no panel needs to be open, and *"Run Saved Query"* in the command palette offers the same list. Running one opens a normal Data Viewer panel, so filtering, editing, export and everything else works as usual, and the values entered last are remembered as the defaults for the next run.

    - **Placeholders are typed, so a value cannot break out of the statement.** Each placeholder is text, number, identifier or raw SQL: text is quoted and its quotes doubled, a number is rejected unless it really is one (`1; DROP TABLE t` never reaches the database), an identifier is quoted as one, and only the deliberately chosen *raw* kind is inserted verbatim — flagged as such in the dialog. Substitution ignores `:name` inside string literals, comments and dollar-quoted blocks and never mistakes a `::` cast for a placeholder, and an inserted value that itself contains a `:name` is not substituted again.
    - **Personal or shared with the team.** A query is stored either privately or in a JSON file in the workspace (`.vscode/postgres-query-builder.queries.json`, path configurable) that can be committed to git. The file can be edited by hand and changes are picked up immediately; a query can be moved between both scopes at any time via the context menu, which also offers rename, edit SQL, duplicate and delete.
    - **The SQL is edited in a real editor tab.** *"Edit SQL"* opens the statement as a `.sql` file with syntax highlighting, formatting and multi-line editing instead of squeezing it into a one-line input box; saving the file writes it back to the query and picks up placeholders that were added or removed along the way.
    - **A saved query can be dragged into any editor.** Dropping it inserts the statement at the drop position — exactly as stored, so the `:name` placeholders stay visible and can be filled in by hand. Several queries can be selected and dropped at once; they are inserted one below the other.
    - **A query in a file can be saved without detouring through the Data Viewer.** Statements that already live in a `.sql` file had to be copied into a panel first just to store them. *"Save Query..."* — in the editor context menu, in the title bar of the *"Saved Queries"* view and in the command palette — takes the selection, or the statement around the cursor when nothing is selected, proposes the queried table as the name and asks where to store it; the `:name` placeholders contained in the statement are recognised immediately and reported.
    - **The context menu shows where a query is stored.** *"Move to Workspace"* and *"Move to Personal"* were both offered on every query, so one of them was always a no-op and the current scope was not visible on the item itself. Only the move that actually changes something is offered now, and the tooltip names the scope.

- **The Constraints button now also stores a sort order:** The permanent per-table settings could only pin conditions to the `WHERE` clause — a table that is only useful newest-first had to be re-sorted by hand after every open. The dialog (now *"Permanent Constraints & Sorting"*) has a second section where any number of columns can be added with `ASC`/`DESC`; they are stored per table just like the conditions and applied to the default query as an `ORDER BY` clause, after the `WHERE` clause. The preview in the dialog shows the resulting statement including the sorting, incomplete rows are dropped on save, and a stored sort column that is not part of the current result is kept instead of being silently discarded. Sorting and conditions are stored independently, so clearing one does not affect the other.

## 2.2.2

- **The formatter no longer stops working after a literal that ends with a backslash:** In PostgreSQL a backslash is an ordinary character inside a normal `'…'` literal (`standard_conforming_strings`), but the formatter treated it as an escape. A perfectly valid `LIKE 'W\_%' ESCAPE '\'` therefore swallowed the closing quote, and from that point on the whole file was read with quotes inverted: everything after it was left completely unformatted, and text that was actually inside a string could be reformatted as if it were code — a literal such as `'DISPLAY_'` came back as `' DISPLAY_ '`. Because the safety net compared the input with the output using the same faulty reading, it did not notice. Backslash escapes are now honoured only where PostgreSQL applies them, in `E'…'` literals. The same reading error also affected the detection of the statement under the cursor for *"View Data"* and has been corrected there as well.

- **Clearing a column filter removes it from the query again:** Typing into a filter box and pressing Enter adds the condition to the `WHERE` clause — but emptying the box and pressing Enter did nothing, because only non-empty filter boxes were considered when the query was rebuilt, so the old condition stayed in the SQL and kept filtering. An emptied filter box now drops exactly its own condition; hand-written clauses and the filters of other columns stay untouched.

- **A cell whose value the column cannot store is outlined in red:** Until now a typo was only noticed when saving failed — the whole transaction was rejected and the change had to be found again. An edited cell is now checked as soon as it is left and marked with a red border and a tooltip explaining the problem (text in an `integer` column, `40000` in a `smallint`, six characters in a `varchar(5)`, a string that is not a timestamp, …). Saving stays blocked while any cell is marked, and the indicator next to the buttons shows how many values still need fixing.

    - **The rules come from the database, and so does the verdict for everything else.** Each result column now carries its real type including the modifier (`character varying(5)`, `numeric(10,2)`, `smallint`) as reported by `format_type()`, so numbers, ranges, text lengths, booleans and UUIDs are checked instantly in the grid without asking the server. Types whose text format only PostgreSQL can judge — timestamps, dates, intervals, JSON, enums, arrays, network and custom types — are handed to the database, which tries to cast the entered text and reports its own error message as the reason. That check runs once per edited cell (not per keystroke) and never writes anything.

- **One Data Viewer for both entry points — every feature is offered whenever it is possible:** Opening a table from the Table Explorer and running *"View Data"* on a `SELECT` used to open two different panels: the first was fully featured, the second was a read-only grid where editing, inserting, deleting, permanent constraints, column mappings and the relation metadata (primary keys, foreign-key navigation, referencing tables) were simply unavailable. Both now use the same panel and the same data path — the table view is just a panel that starts with the default query of that table — and what the panel offers is derived from the result itself instead of from how it was opened:

    - **Ad-hoc query results are editable.** PostgreSQL reports the source relation and column for every result field that maps 1:1 onto a table column, so the viewer resolves each column back to its origin (through aliases, joins and sub-selects) and writes changes back to the right table — column by column. Computed columns, aggregates and literals stay read-only, and a banner explains why when a result cannot be edited at all.
    - **Results joined from several tables can be edited in place.** Changes are grouped per source table and committed in a single transaction; the SQL preview shows exactly the statements that will run. Inserting and deleting rows stays reserved for results that come from exactly one table.
    - **Rows without a primary key are handled safely.** When the result carries every primary-key column, rows are matched by that key. Otherwise they are matched by all of their displayed values, a warning banner is shown, and each `UPDATE`/`DELETE` is verified to affect exactly one row — otherwise the whole transaction is rolled back and nothing is changed.
    - **Views, materialized views and results of unknown origin are recognized as read-only** instead of failing at commit time; constraints and column mappings still work when the result comes from a single relation.
    - **Table-bound features follow the query.** Running a query against a different table in an open panel switches the panel to that table: relation metadata, foreign-key navigation, permanent constraints and column mappings follow along. Conversely, a table panel showing an arbitrary query no longer pretends its rows still belong to the original table.
    - **Each panel has its own query history** instead of one shared bucket, the connection is established before a "View Data" panel opens (it previously opened against no connection), a failed query releases the loading spinner instead of leaving it running forever, and saving/discarding changes re-runs the query you are looking at instead of resetting the panel to `SELECT * FROM <table>`.
    - **The exact row count is only computed when it is useful.** The plain table view still shows *"Showing X of Y rows"*; for an arbitrary query the viewer shows how many rows are loaded and counts the full result only when you click the indicator — counting an expensive query is no longer forced on every run.

- **The Save preview shows the warnings and lets the statements be edited before they run:** The note about how rows are matched used to sit permanently in a banner above the grid, where it was easy to overlook and took up space while browsing. It is now shown where it matters — in the confirmation popup that opens when you press **Save**, together with a warning when the active connection is no longer the one the data was loaded from. The previewed statements are no longer a read-only text: they can be edited in place (**Reset** restores the generated version) and are then executed exactly as written, as a single transaction that either applies completely or not at all.

- **Column headers show at a glance how safely a column can be edited:**
 The header background now encodes where a column comes from — the **plain editor background** for a column that maps onto a table column whose rows are identified by a primary key (changes are written back exactly), a **greyed** shade for a column that maps onto a table column but whose rows can only be matched by all of their displayed values (a change is rejected unless it affects exactly one row), and a **blue tint** for a computed column, aggregate or literal that has no source table and therefore cannot be written back at all. The shades are mixed from the active colour theme, so they stay readable in light, dark and high-contrast themes. In a result joined from several tables each column is judged by its own table.

- **The "View Data" result no longer offers actions it cannot perform:** In the read-only custom-query view the **Constraints** button and the cell context-menu entries *"Create Custom Mapping…"* / *"Manage Mappings…"* were shown even though that panel has no table to attach them to — the messages they sent were dropped. Saving a permanent constraint there even overwrote the query bar with a nonsense `SELECT * FROM ""` and left the grid stuck on the loading spinner. All three affordances are now hidden whenever the view has no source table.

- **`INSERT` export from a "View Data" result uses a usable table name:** Because such a result has no source table, the INSERT export pre-filled the target with an empty quoted identifier and produced `INSERT INTO "" …`. It now falls back to `exported_data`, which can be edited in the export dialog as usual.

- **The `alwaysQuote` setting now also applies to the "View Data" result:** The custom-query panel never received the setting, so identifiers added by column filters, ORDER BY and the context-menu actions were quoted differently there than in a regular table view.

- **Export works again in a Data Viewer opened from a SELECT statement:** In the read-only custom-query view (the "View Data" command on a `SELECT`), the Export dialog was inert — clicking **Browse** opened no folder picker, the saved export defaults were never loaded, and **Export** itself did nothing at all. That panel has its own message handler which only knew about the query commands, so every export message from the webview was silently dropped. It now forwards `browseExportLocation`, `getExportDefaults`, `saveExportDefaults` and `exportData` to the same handlers the regular table view uses, so browsing for a folder, saving defaults and exporting the full result set behave identically in both views. If such a panel has no query text to export, the export now reports a clear error instead of trying to read from a non-existent table.

## 2.2.1

- **Files with Windows line endings (CRLF) are no longer skipped by the formatter:** The renderer joins its output with `\n`, so in a CRLF file the `\r` inside multi-line block comments and multi-line string literals was lost. Because such tokens are compared byte-for-byte, the safety net (correctly) rejected the result and reported *"formatting would have changed the code at token N: expected `/****…` but the formatted output had `/****…`"* — two comments that looked identical but differed in their line endings. Formatting now runs on LF-normalised text and restores the file's original CRLF endings afterwards.

- **Comment whitespace no longer disables formatting:** Trailing blanks inside a block comment (or after a `--` comment) were trimmed by the final formatting pass, which again changed a token that was compared verbatim. Comment tokens are now compared whitespace-insensitively — exactly as the safety net always documented — so re-indenting or trimming a comment is accepted, while any real change to a comment's text is still rejected.

- **Multi-line string literals inside a dollar-quoted body keep their payload:** When a `$body$ … $body$` block was re-indented, every physical line was shifted — including the interior lines of a multi-line string literal (e.g. a JSON template `'{\n  "messages": []\n}'`), which silently changed the string's content. Indentation is now only applied to lines that do not continue a string, dollar-quoted or quoted-identifier literal.

## 2.1.4

- **A `SELECT` is no longer collapsed onto one line when a function call was deliberately split across lines with a compound argument:** A single-statement `SELECT` (for example the body of a `LANGUAGE sql` function) was treated as a "simple" `SELECT` and rendered on a single line even when the author had written a function call across several lines, such as `hashtext(COALESCE(a, '') || COALESCE('::' || b, ''))`. A function call whose single argument is a compound expression (it contains a top-level operator like `||`, `+`, …) and which the author split across multiple source lines now keeps its multi-line layout — the call wraps its argument onto its own indented line and the surrounding `SELECT` is no longer flattened. Calls written on one line, and multi-line calls whose argument is a single simple value (e.g. `foo(\n bar\n)`), still collapse as before.

- **Multi-line SQL statements inside a dollar-quoted `format()` template are now reformatted:** A dollar-quoted body was only reformatted when it contained a PL/pgSQL block (`BEGIN`/`DECLARE`). A dynamic-SQL template such as `format($query$ SELECT … FROM … WHERE x = %L $query$, …)` was therefore left with its original (often misaligned) indentation. The formatter now also recognises a dollar-quoted body whose first significant word starts a SQL statement (`SELECT`, `WITH`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`) and reformats it like the surrounding code, so the embedded query gets proper clause/column/`JOIN`/`WHERE` layout. For such a statement template the opening and closing `$query$` tags are placed on the same indentation level and the query itself is indented one level deeper; PL/pgSQL block bodies (`BEGIN`/`DECLARE`) keep their content on the same level as the tags as before. The detection only applies to multi-line bodies: a short single-line body (e.g. `AS $$ SELECT 1 $$`) and bodies that are plain text, JSON or regex patterns are still emitted verbatim.


- **`format()` placeholders (`%L`, `%I`, `%s`) are no longer broken apart when a dollar-quoted body is reformatted:** When a PL/pgSQL routine built dynamic SQL with `format($outer$ … WHERE x = %L … $outer$, …)`, the formatter recursed into the dollar-quoted body, tokenized `%L` as the modulo operator `%` followed by the identifier `L`, and inserted a space between them — turning `%L` into `% L`. Because `format()` treats `%L`/`%I`/`%s` as single placeholders, this silently changed the generated SQL (and the semantic safety net could not catch it, since `%L` and `% L` tokenize identically). The tokenizer now recognises a `%` immediately followed by a `format()` type character (`s`, `I` or `L`) as one indivisible token, so the placeholder is emitted verbatim. Modulo expressions written with spaces (`a % b`), `%TYPE`/`%ROWTYPE` attribute references, the literal `%%`, and a `%` applied to a longer identifier (`a % system`) are all unaffected.


- **`listThresholds.createFunction` (and `createProcedure`) now takes effect even when `preserveSingleLineRoutineHeaders` is enabled:** When a `createFunction` threshold of `"0, 1"` (or similar "always wrap") was configured in `.pgformat.json`, the CLI formatter left single-line function headers unchanged because the `preserveSingleLineRoutineHeaders: true` default short-circuited the threshold check before it could run. The fix makes the single-line shortcut yield to the threshold: if the parameter-list threshold demands multi-line output for the given number of parameters, the shortcut is skipped and the normal formatting logic expands the parameters to individual lines. Behaviour is unchanged for zero-parameter functions and for parameter counts that fall within the "follow source" band.

- **CLI and VSIX now share the same formatter defaults:** The code-level `DEFAULT_THRESHOLDS` in `plpgsqlFormatter.ts` were out of sync with the VS Code setting defaults defined in `package.json`. When no `.pgformat.json` was present the CLI used the old code defaults, producing different output than the VSIX extension for the same SQL. All thresholds are now aligned with the `package.json` values: `createFunction`/`createProcedure`/`createTable` default to `0, 1` (all parameters/columns wrap), `createType` to `1, 2`, `selectColumns` to `1, 3`, `insertColumns`/`arrayLiterals`/`inLists` to `2, 10`, `booleanGroups`/`joinConditions`/`ifConditions`/`caseConditions` to `1, 3`, `operatorChains` to `1, 6`, and `caseWhenThen`/`exceptionWhenThen`/`ifElse` to `0, 3`.

- **Configurable path to the formatter rules file (`postgresQueryBuilder.format.configPath`):** A new setting lets you point the extension at a formatter-rules JSON file anywhere, instead of only `.pgformat.json` in the workspace root. An absolute path is used as-is; a relative path is resolved against the workspace root; leaving it empty keeps the previous behaviour (`.pgformat.json` in the workspace root). The file uses the same schema as `.pgformat.json`, and its values still take precedence over personal VS Code settings.

## 2.1.3

- **Line comments directly attached to an operator (`||--`) no longer swallow the following code:** When a `--` comment followed an operator with no space (e.g. `TO_CHAR(…) || '.' ||-- P_TAG_KG`), the tokenizer mistook `||--` for a single operator, so the `--` never started a comment. As a result the code on the following lines was silently merged into the (non-)comment when formatting, effectively commenting out real code. In PostgreSQL `--` and `/*` always begin a comment and can never appear inside an operator; the tokenizer now stops an operator run before either marker, so the comment is recognised and the code is preserved.

- **Safety net now detects this class of corruption:** Because the previous tokenization produced no comment token at all, the formatter's semantic safety net could not see that code had been absorbed and let the bad output through. With the comment now tokenized correctly, the safety net again guarantees that formatting never turns live code into comment text.

They are now indented one level deeper inside the parentheses, matching the established behaviour of `FROM (SELECT …)` subqueries. The fix applies at any nesting depth and inside PL/pgSQL blocks.

The newline before such a comment is now preserved so the comment keeps its own line.

  - `createTable` – `CREATE TABLE` column list (`1, 4`)
  - `returnsTable` – `RETURNS TABLE(…)` column list of a `CREATE FUNCTION` (`1, 4`)
  - `functionCall` – function/procedure call argument list (`1, 4`)
  - `selectColumns` – `SELECT` column and `INTO` target list (`1, 2`)
  - `fromTables` – `FROM` table list in comma style (`FROM a, b, c`) (`1, 4`)
  - `insertColumns` – `INSERT` column and `VALUES` list (`2, 6`)
  - `arrayLiterals` – `ARRAY[…]` literals including nested element arrays (`4, 12`)
  - `inLists` – `IN (…)` value lists (`4, 12`)
  - `booleanGroups` – parenthesised boolean groups (`(a AND b OR c)`) (`1, 2`)
  - `joinConditions` – `JOIN … ON … AND …` conditions (`1, 2`)
  - `ifConditions` – `IF`/`ELSIF` conditions (`1, 2`)
  - `caseConditions` – `CASE … WHEN` conditions (`AND`/`OR` inside a `WHEN` condition) (`1, 2`)
  - `operatorChains` – operator chains (`+`, `-`, `*`, `/`, `||`) in an expression (`1, 8`)
  - `caseWhenThen` – collapsing a `CASE … WHEN … THEN` block (`inlineMax` only; `0` = never collapse)
  - `exceptionWhenThen` – collapsing an `EXCEPTION WHEN … THEN` block (`inlineMax` only; `0` = never collapse)
  - `ifElse` – collapsing an `IF … ELSE … END IF` block (`inlineMax` only; `0` = never collapse)
- **Break the `CREATE TABLE` column list:** the column list of a `CREATE TABLE … (…)` is broken according to the `createTable` thresholds (default `1, 4`).
- **Break the `RETURNS TABLE(…)` column list:** the column list of a `RETURNS TABLE(…)` of a `CREATE FUNCTION` is broken like a parameter list according to the `returnsTable` thresholds (default `1, 4`) (one column per line, closing parenthesis on its own line); there is no space between `TABLE` and the parenthesis.
- **`SELECT` columns and the `FROM` table list follow their thresholds:** the `SELECT`/`INTO` list (`selectColumns`, default `1, 2`) and the comma-separated `FROM` table list in the old style (`fromTables`, default `1, 4`) now follow their own thresholds instead of the source layout alone.
- **Break `ARRAY[…]` literals:** the element lists of `ARRAY[…]` literals (including nested arrays) are broken according to the `arrayLiterals` thresholds (default `4, 12`); index accesses (`arr[i]`) stay on one line as before. (Note: a simple `SELECT` statement with only one ARRAY value still stays on one line because of `simpleSelectSingleLine`.)
- **Break `IN (…)` value lists:** `IN` value lists are broken according to the `inLists` thresholds (default `4, 12`).
- **Conditions controllable per construct:** breaking at `AND`/`OR` can be configured separately for `JOIN … ON …` (`joinConditions`), `IF`/`ELSIF` (`ifConditions`) and `CASE … WHEN` (`caseConditions`). With the defaults (`1, 2`) the previous behaviour is preserved (from two sub-conditions on, each `AND`/`OR` on its own line); higher thresholds keep short conditions on one line.
- **Break long operator chains:** an expression that chains many operands with `+`, `-`, `*`, `/` or `||` (for example a long sum of `CASE … END`) is broken according to the `operatorChains` thresholds (default `1, 8`) — every operator starts its own indented line (operator-leading), analogous to boolean groups. A single `CASE … END` counts as one operand.
- **Format the `INSERT` column and `VALUES` list consistently:** the column list and the `VALUES` list of an `INSERT` are decided together and always broken the same way — according to the `insertColumns` thresholds (default `2, 6`).
- **Collapse structural blocks (`caseWhenThen`, `exceptionWhenThen`, `ifElse`):** small structural blocks can be collapsed onto one line. A block is rendered on one line if the number of its statements (`;`) is less than or equal to `inlineMax` and the body contains neither comments nor nested blocks (`IF`/`CASE`/`LOOP`/`BEGIN`/`DECLARE`/`EXCEPTION`):
  - `ifElse` – `IF … THEN … [ELSE …] END IF;` (for example `IF a THEN x := 1; END IF;`)
  - `caseWhenThen` – `CASE … WHEN … THEN … END CASE;`
  - `exceptionWhenThen` – `EXCEPTION WHEN … THEN …;` (the `END` of the enclosing `BEGIN` stays on its own line)
  
  With the default `inlineMax = 0` nothing is ever collapsed (the previous multi-line behaviour is preserved); from `inlineMax ≥ 1` on, correspondingly small blocks are rendered on one line.

## 2.0.0

- **Configurable PL/pgSQL formatter:** a new formatter for SQL and PL/pgSQL code, reachable through the standard VS Code function **"Format Document"** (`Shift+Alt+F`), the command **"PostgreSQL: Format PL/pgSQL"** (Command Palette and editor context menu), a **"Format PL/pgSQL"** button in the SQL editor and optionally on save. The formatter indents PL/pgSQL blocks (`DECLARE`/`BEGIN`/`END`, `IF`/`ELSIF`/`ELSE`, `LOOP`), breaks SQL clauses (`SELECT`/`FROM`/`WHERE`/`JOIN`/`ORDER BY` …) and column lists in a structured way, unifies the casing of keywords and data types and leaves strings, comments and user-placed blank lines untouched. `CASE` expressions are treated correctly as an expression (no false break at `ELSE`/`END`); function bodies in `$$ … $$` are formatted recursively. The output is a pure re-layout of the existing tokens, so no part of a statement can get lost, and it is idempotent (formatting again changes nothing).
  - Configurable through the following settings (defaults in brackets): `postgresQueryBuilder.format.enable` (on), `postgresQueryBuilder.format.formatOnSave` (off), `postgresQueryBuilder.format.keywordCase` (`upper`), `postgresQueryBuilder.format.identifierCase` (`preserve`), `postgresQueryBuilder.format.dataTypeCase` (`upper`), `postgresQueryBuilder.format.indentStyle` (`space`), `postgresQueryBuilder.format.indentSize` (`2`) and `postgresQueryBuilder.format.commaStyle` (`trailing`). The formatter is registered for the language ids `sql`, `postgres` and `pgsql`.
  - **Formatter improvements:**
    - **Routine headers (`CREATE FUNCTION`/`PROCEDURE`):** the header is now formatted in a structured way — parameter lists are broken depending on their length (see `format.listThresholds`, entry `functionCall`), `RETURNS …` stays on the line of the closing parenthesis, characteristics (`LANGUAGE`, `STABLE`, `SECURITY DEFINER`, `SET …` …) each get their own indented line, `AS` starts in column 0, and the body (`DECLARE`/`BEGIN`/`END`) is not indented any further.
    - **`EXCEPTION … WHEN … THEN` blocks** in PL/pgSQL are now broken and indented correctly (`EXCEPTION` on the `BEGIN` level, `WHEN` one level deeper, the handler body one level deeper again).
    - **`IF [NOT] EXISTS`** (for example `CREATE SCHEMA IF NOT EXISTS …`, `DROP TABLE IF EXISTS …`) is no longer mistaken for a PL/pgSQL `IF` block and broken.
    - **Type modifiers** such as `VARCHAR(500)` or `NUMERIC(10,2)` keep their parentheses without an inserted space.
    - **Clause words inside function calls** (for example `substring(… FROM 1 FOR 500)`) are no longer broken as if they were SQL clauses; breaking at `SELECT`/`FROM`/`WHERE`/… only applies in a real SQL context (subqueries).
    - **`ARRAY[…]` literals** stay on one line (commas inside the square brackets do not trigger a list break).
    - **Configurable argument and parameter breaking:** call and parameter lists are always kept on one line with at most `inlineMax` arguments and always broken across lines from `multilineMin` arguments on; in between, the layout chosen in the source is preserved (entry `functionCall` in `format.listThresholds`).
    - **Blank lines preserved exactly:** blank lines placed by the user are preserved exactly by default (`blankLines: preserve`); alternatively they can be collapsed to at most one (`collapse`).
    - **Simple `SELECT` statements** (one column, at most one table, at most one `WHERE` condition, no `JOIN`/`GROUP`/`ORDER`) stay on a single line by default (`simpleSelectSingleLine`).
    - **Routines written on one line stay on one line:** if a `CREATE [OR REPLACE] FUNCTION`/`PROCEDURE` statement is written entirely on a single line in the source (including the body in `$$ … $$`), it is no longer broken into the multi-line routine header but stays on one line (keywords and data types are still unified, the body stays unchanged). Example: `CREATE FUNCTION pk.g_pair() RETURNS VARCHAR LANGUAGE SQL IMMUTABLE AS $$ SELECT 'X'; $$;` is preserved as is. Routines written across several lines are still formatted in a structured way.
    - **`SELECT`/`INTO` lists: a single value stays on the line, several are broken:** if only one expression is selected, it now stands right behind the `SELECT` keyword (`SELECT 1`); with several expressions the list is split across lines as before. The same applies to the `INTO` target list in `SELECT … INTO`. `INTO` (for example `INTO STRICT v_dummy`) now generally starts a line of its own (only `INSERT INTO …` stays on one line).
    - **`AND` conditions each on their own indented line:** in `WHERE`, `HAVING` and `ON` conditions every top-level `AND` now starts a new line, indented one level deeper. The exception is the `AND` that belongs to a `BETWEEN` — `… AND x BETWEEN y AND z` stays together on one line.
    - **`%TYPE`/`%ROWTYPE` without spaces:** attribute type references such as `bos_mitarbeiter%ROWTYPE` or `t.c%TYPE` are now attached directly to the name without spaces around the `%` (`v_mitRec bos_mitarbeiter%ROWTYPE;`). The modulo `%` as an operator (`a % b`) is unaffected and keeps its spaces.
    - **Normalise type names:** verbose, multi-word type names are unified to their short form while formatting — `character varying` → `varchar`, `bit varying` → `varbit`, `timestamp without time zone` → `timestamp`, `timestamp with time zone` → `timestamptz`, `time without time zone` → `time`, `time with time zone` → `timetz` (type modifiers such as `(500)` are kept, for example `character varying(500)` → `varchar(500)`). Controlled through the new setting `postgresQueryBuilder.format.normalizeDataTypes` (default: on).
    - **Trailing line comments stay on their line:** a `--` comment that stands at the end of a line in the source (for example behind the closing `;` of a single-line function) is no longer moved onto a line of its own but stays attached to that line. Comments that already stand on their own line keep their own line.
    - **Blank lines before statements such as `CREATE`/`UPDATE`/`INSERT` are preserved:** blank lines placed by the user before a statement that does not start with a clause keyword (for example several empty lines between two `CREATE FUNCTION` definitions) used to be removed. They are now preserved exactly, as with the other clauses.
    - **Blank lines before comments are preserved:** a blank line placed by the user directly before a standalone `--` comment (for example before a section heading in the `DECLARE` block) used to be removed; it is now kept.
    - **Prefixed string literals such as `E'…'` stay unchanged:** escape, bit, hex and unicode string literals (`E'\n'`, `B'1010'`, `X'1f'`, `U&'\0041'` and their lower-case spellings) are now recognised as a single token. Previously the prefix was separated from the string content (`E '\n'`), which produced broken SQL.
    - **Structured formatting of `CASE` expressions:** a `CASE` expression that stands entirely on one line in the source stays on one line (`CASE WHEN a AND b THEN 1 ELSE 0 END`). A `CASE` expression written across several lines is now structured: every `WHEN` (and `ELSE`/`END`) starts its own line, `WHEN`/`ELSE` one level deeper than `CASE`, `END` back on the `CASE` level. If a `WHEN … THEN …` clause is on one line in the source, it stays on one line; if it spans several lines, the result starts on its own, more deeply indented line after `THEN`. If the condition of a `WHEN` consists of several top-level sub-conditions joined with `AND`/`OR`, every further sub-condition is broken onto its own indented line, `THEN` then stands alone on a line and the result below it — the `AND` belonging to a `BETWEEN` stays on the line. The `CASE` statement form (`CASE … END CASE;` with statements such as `IF … END IF;` in the body) is excluded from this and detected correctly — nested `IF`/`LOOP`/`BEGIN` blocks are counted when looking for the matching `END`, so the statement body is no longer pulled onto one line by mistake (and "commented out" behind a line comment). The `CASE` statement form is also indented in a structured way: `CASE`/`END CASE` stand on the block level, every `WHEN`/`ELSE` one level deeper, and the respective statement body (assignments, nested `IF`/`LOOP` blocks …) starts on a new line after `THEN` and is indented one more level (blank lines and trailing comments are preserved).
    - **Structured formatting of `FOR … IN <SELECT …> LOOP` loops:** for a loop over a query, `FOR … IN` still stands on its own line, the query (`SELECT`/`FROM`/`WHERE`/…) is now indented one level deeper, and the `LOOP` keyword starts its own line at the level of the `FOR` (instead of being appended to the last query line). The loop body is indented as before. Simple loop headers (`FOR i IN 1..10 LOOP`, `WHILE … LOOP`) stay compact on one line.
    - **Break parenthesised boolean groups:** a parenthesised condition that is joined at the top level with `AND`/`OR` (for example `AND (a <> 1 OR b IS NOT NULL)`) is now formatted across several lines: the opening parenthesis stays at the end of the line, every operand and every `AND`/`OR` stands on its own line indented one level deeper, and the closing parenthesis is outdented again. `OR` — like `AND` before — starts its own line inside conditions (except in `CREATE OR REPLACE`). Pure groups without a boolean link (`(a + b)`, `IN (1, 2, 3)`, `(x BETWEEN 1 AND 5)`) stay on one line.
    - **Several formatting passes:** the formatter is now applied to its own output up to ten times, until nothing changes any more. This way, line breaks that only appear during formatting (for example in nested boolean groups) are indented cleanly as well, and the result is idempotent.
    - **`THEN` for multi-line `IF`/`ELSIF` conditions:** if an `IF` or `ELSIF` condition is broken across several lines by `AND`/`OR`, the `THEN` now stands on its own line at the level of the `IF`/`ELSIF` (instead of being appended to the last condition line). Single-line conditions keep `THEN` at the end of the line.
  - **New settings (defaults in brackets):** `postgresQueryBuilder.format.blankLines` (`preserve`), `postgresQueryBuilder.format.simpleSelectSingleLine` (`true`), `postgresQueryBuilder.format.listThresholds` (a table per construct) and `postgresQueryBuilder.format.normalizeDataTypes` (`true`).

## 1.3.0

- **"View Data": column headers and the filter row stay visible while scrolling (sticky):** when scrolling vertically through the data, both the column headers and the filter row below them now stay pinned to the top of the table. Since the header is two lines high (column name + data type) and its height depends on the content, the actual header height is measured and the filter row is docked exactly below it (recalculated when the window is resized). A separator line that scrolls along keeps the pinned rows clearly separated from the data area.

- **"View Data": columns are shown immediately, while the data is still loading:** when a table is opened, the column header is now shown as soon as the column information is available — that is, while the (possibly slow) `SELECT` and `COUNT` queries are still running. This makes it possible to open the **"Constraints"** dialog and add a permanent condition before the data has fully loaded, for example. Technically the extension sends a separate `columnsLoaded` message to the view right after fetching the columns (only for the first page of a regular table view; "Load More" and custom query results are unaffected); the loading indicator for the data stays visible until the rows have arrived.

- **"View Data": permanent table constraints:** the new **"Constraints"** button in the toolbar of the Data Viewer stores fixed `WHERE` conditions per table that are **appended automatically to the default query every time this table is opened** (for example `CURRENT_TIMESTAMP BETWEEN valid_from AND valid_to` to always show only the currently valid records). The condition editor uses **the same design as "+ Add fixed condition" in the JOIN dialog**: every condition consists of a left operand, an operator and a right operand; operands are entered either through a dropdown as a **column** of the table or as a **free value/expression** (for example `'TGB'` or `CURRENT_TIMESTAMP`). The available operators are `=`, `<>`, `<`, `<=`, `>`, `>=`, `LIKE`, `ILIKE`, `BETWEEN` (two right operands) and `IS NULL`/`IS NOT NULL` (without a right operand). A live preview shows the resulting query; **"Save & Apply"** stores the conditions permanently and reloads the view immediately. The conditions are kept in a structured form in the global state of the extension per `schema.table` and still count as a regular `WHERE` clause, so the records stay editable in the Data Viewer (primary and foreign key metadata is still loaded).
- **"View Data": `IS NULL` / `IS NOT NULL` filters from the column right-click menu:** the context menu of a column header in the Data Viewer now offers the entries **"Add `<column>` IS NULL to WHERE"** and **"Add `<column>` IS NOT NULL to WHERE"**. They add an `IS NULL` or `IS NOT NULL` condition for the chosen column to the current `WHERE` clause with a single click; an existing condition on the same column is replaced. The changed query runs immediately.
- **Custom mapping: multi-column links (composite keys):** custom column mappings can now match several column pairs in order to model composite keys, for example `a.order_id = b.order_id AND a.tenant_id = b.tenant_id`. The mapping dialog has a new section **"Additional column matches"** with the button **"+ Add column match"**, which uses the same interaction as the build JOIN dialog: pick the source column from a dropdown and type the target column with typeahead; all pairs are combined with `AND`. When deriving JOINs, every column pair produces its own ON condition, so the JOIN dialog is pre-filled with the complete composite link automatically. Reverse mappings swap source and target column of all pairs correctly. Existing single-column mappings stay compatible.
- **"View Data": UPDATE/DELETE for tables without a primary key:** for tables without a primary key, changes and deletions in the Data Viewer used to fail or produced an empty `WHERE` clause. In that case the affected row is now identified through **all column values** (full-row match), so that `UPDATE` and `DELETE` statements hit the right row. `NULL` values in the identification are mapped correctly to `IS NULL` (instead of `= NULL`) — in the SQL preview as well as in the parameterised commit. As a safeguard, a statement with a completely empty `WHERE` clause is rejected (with a rollback of the transaction) so that all rows can never be changed or deleted by accident. Tables with a primary key behave as before (identification still uses the PK columns only).
- **JOIN dialog: the same table can be added several times (self-join):** the JOIN dialog can now add the same table more than once, each time with its own alias and its own join condition (for example for self-joins such as `employees e LEFT JOIN employees m ON m.id = e.mgr_id`). When adding through "+ Add tables…", tables that are already part of the join are no longer filtered out but shown in the picker with the hint "already in join — adds another instance". Every added instance gets a unique alias and is treated as an independent table; by default the additional instance is inserted as a `CROSS JOIN`, so that the join condition can afterwards be set freely against any earlier table (including another instance of the same table).
- **JOIN dialog: ON conditions are pre-filled when a table is added again or several times:** a table added again or several times now gets the same automatically derived join conditions as on the first add. The assignment now consistently uses the table and column names from the foreign key and custom mapping edges (instead of a single table index), so that a second instance of the same table is connected to the matching earlier table correctly as well (including self-joins over self-referencing foreign keys).
- **JOIN dialog: alias numbering releases freed suffixes again:** if a previously added table (for example with the alias `table2`) is removed and added again, it gets `table2` back instead of continuing with `table3`. The uniqueness check now only considers the aliases of the currently visible tables, so numbers freed by removing a table are handed out again.
- **JOIN dialog: fixed extra conditions in the ON clause:** the new button **"+ Add fixed condition"** adds arbitrary fixed conditions to the ON clause per join, for example `CURRENT_TIMESTAMP BETWEEN t.valid_from AND t.valid_to` or `t.type = 'TGB'`. Every condition is assembled comfortably from three parts: left operand, operator and right operand. Operands are either picked from a dropdown as a **column** (qualified with the table alias) or entered as a **free value/expression** (for example a string literal `'TGB'` or a SQL expression such as `CURRENT_TIMESTAMP`). The available operators are `=`, `<>`, `<`, `<=`, `>`, `>=`, `LIKE`, `ILIKE`, `BETWEEN` (two right operands, joined with `AND`) and `IS NULL`/`IS NOT NULL` (without a right operand). The fixed conditions are appended to the remaining ON conditions with `AND` in the preview and in the generated statement and survive reordering of the tables.
- **JOIN dialog: automatically inserted custom mapping conditions can be edited:** the extra conditions pre-filled from custom column mappings, which used to be shown read-only, can now be turned into an editable fixed condition through an **"Edit"** button. The condition is transferred into the new condition editor (left operand / operator / right operand): the column stays an alias-qualified column selection, the value is taken over as a freely editable literal. Operator and operands can then be adjusted at will; the original read-only row is removed in the process so that the condition does not appear twice.

## 1.2.0

- **"View Data": variables after `LIMIT`/`OFFSET` and PL/pgSQL record fields are recognised:** the variable dialog now also recognises variables that stand as the row count behind `LIMIT` or `OFFSET` (for example `LIMIT pi_max_history` → `pi_max_history` is prompted for). In addition, field accesses on PL/pgSQL record variables (for example `pi_employeeObj.emplId` in `… = pi_employeeObj.emplId`) are treated and replaced as a single variable. To tell them apart from real, table-qualified columns (`lbe.lbe_mit_id`), all table names and aliases from the `FROM`/`JOIN` clauses (including subqueries) are collected: if the identifier before the dot is **not** a known table or alias name (and there is no function call `x.y(…)` and no longer chain `x.y.z`), the dotted identifier counts as a record variable. Numeric `LIMIT` literals (`LIMIT 100`) and correlated references to an outer table alias stay untouched.
- **Show and change the `search_path`:** the title bar of the table tree view now has a button **"Show / Edit search_path"** (also reachable from the Command Palette as *PostgreSQL: Show / Edit search_path*). It shows the currently effective `search_path` of the active connection in an input field and allows it to be changed (a comma-separated list of schemas). An empty field restores the server default. The new path is applied to all connections of the pool through `set_config('search_path', …)` (as a parameter, therefore injection-safe) — the pool is rebuilt for this and the metadata cache is cleared. The tree view is refreshed afterwards so that the changed schema resolution (qualification of tables) takes effect immediately.
- **Relations grouped by type in the tree view:** under every schema the relations are now grouped in their own, automatically expanded sub-nodes: **Tables**, **Views**, **Materialized Views** and **Foreign Tables** (in that order). Only categories that actually contain relations are shown; every category and every schema is expanded by default. The relation icons differ per type. With an active search filter, only the categories that contain at least one matching relation stay visible.
- **Views are visible in the table tree view:** (rule) views are now shown in the tree view, the table search, the JOIN dialog and the typeahead picker in addition to tables and foreign tables. The listing takes the `table_type` `'VIEW'` from `information_schema.tables` into account for this. **Materialized views** now appear in the same places as well: since PostgreSQL does not expose them through `information_schema`, they are additionally read from `pg_matviews` and merged with a `UNION`.
- **`search_path` detection when opening tables corrected:** whether a table has to be qualified with its schema is now determined reliably from `current_setting('search_path')` (equivalent to `SHOW search_path`) instead of from `current_schemas(false)`. The latter only reflects the actually resolved path of the currently executing session and on pooled connections sometimes returned an **empty list**, even though the schema (for example `leda`) was clearly part of the `search_path`. As a result, tables were qualified unnecessarily (`SELECT * FROM leda.table` instead of `SELECT * FROM table`). The `search_path` string is now parsed by the extension itself (comma separation, double-quoted identifiers including `\"\"` escaping, and the resolution of the special entry `$user`/`\"$user\"` to the current user). The diagnostic log now shows the raw `search_path` string and the resolved user.
- **Diagnostic output in the "PostgreSQL Query Builder" output channel:** important operations are now logged to the VS Code output channel **"PostgreSQL Query Builder"** (time-stamped and grouped by area). Among the logged items are the server `search_path` determined when connecting (`SHOW search_path`), the connection data (host/resolved IP, port, database, user, display schemas), and per opened table the `search_path` queried at runtime (`current_schemas(false)`) together with the derived table reference including the reason (whether and why the schema is prepended). This makes it easier to diagnose cases in which a table is opened from the wrong schema.
- **Schema qualification when opening tables outside the `search_path`:** when a table is opened, the generated `SELECT` is now qualified with the schema correctly (`SELECT * FROM leda_dev.table` instead of `SELECT * FROM table`) if the schema is configured on the connection for display in the tree but is not part of the actual PostgreSQL `search_path`. Previously the schema list stored on the connection (a pure display filter) was mistakenly interpreted as the `search_path`. As a result, a foreign table from `leda_dev` was queried without a schema prefix and the identically named local table from the `search_path` schema (`leda`) was opened instead. Only the `search_path` determined at runtime (`current_schemas(false)`) is authoritative now.
- **Foreign tables now appear in the table tree view:** foreign tables (for example tables attached through `postgres_fdw`) were not shown in the tree view, the table search, the JOIN dialog and the typeahead picker when the PostgreSQL server reports them as `'FOREIGN TABLE'` in `information_schema.tables` (server versions < 9.5). The filters now take both spellings (`'FOREIGN'` and `'FOREIGN TABLE'`) into account through a shared constant, so that foreign tables are listed like normal tables regardless of the server version.
- **Edit a connection without entering the password:** when editing an existing connection (for example to adjust only the port, host or database), the password field no longer has to be filled in again. If the field is left empty, the password previously stored for this connection is reused automatically instead of being overwritten with an empty value. If a new password is entered, it replaces the old one as before. For new connections the behaviour is unchanged.

A table is grabbed at its drag handle (☰) and dropped at the desired position; the join conditions configured so far are preserved — even when a table is moved to the first position (FROM), the join condition is automatically assigned to the later table instead of being lost.
- The **JOIN dialog** can now **add further tables**: a click on "+ Add tables…" opens a multi-selection of all available tables (if tables were selected in the tree view beforehand, they are taken over directly). The chosen tables are appended to the end of the table list. Join conditions for the new tables are pre-filled automatically from existing foreign keys to the tables already present; the order, aliases and conditions of the existing tables stay unchanged. Tables that are already part of the join are skipped, aliases are made unique where necessary.
- The **JOIN dialog** can now **remove tables** again: every table row has an ✕ button. On removal the corresponding join clause and all conditions of other tables that refer to the removed table are cleaned up as well; the last remaining table cannot be removed. A previously removed table can be added again through "+ Add tables…".
- The **JOIN dialog** now also pre-fills join conditions from **custom column mappings** — no longer only from database foreign keys. If a custom mapping `A.column → B.column` exists between two tables involved in the join, a join condition is derived from it automatically (for the initial tables as well as for tables added later). Duplicate conditions (already covered by a foreign key) are avoided.
- The **JOIN dialog** now also takes the **extra conditions** stored in a custom mapping into the ON clause. If a mapping has further conditions besides the column link (for example `status = 'active'`), they are appended to the respective join condition as literal conditions (for example `... ON b.id = a.b_id AND a.status = 'active'`). Values are formatted correctly as a number or as a quoted string literal. The derived extra conditions are shown in the dialog, survive reordering and can be removed individually if needed.
- The **JOIN dialog** can now also be opened when dragging a **single table**: choosing the option **"Join"** on drop opens the interactive JOIN builder with that table as the FROM table. Further tables can then be added through "+ Add tables…" and the join conditions configured (previously only a static `JOIN … ON …` snippet was inserted).
- **JSONB/JSON values are now visible in the Data Viewer:** columns of type `json`/`jsonb` are delivered by the Postgres driver as JavaScript objects/arrays and used to be shown as `[object Object]`. They are now rendered as formatted JSON text — in the table cell as well as in the record dialog ("View full record") and in duplicated rows. The display is consistent with the change detection, so unchanged JSON cells are no longer marked as edited by mistake.
- **"View Data" for SELECTs inside procedures and functions:** in a SQL file (for example a schema script with many procedures and functions) the editor context menu now offers the entry **"View Data"**. On a right-click inside a `SELECT` statement, its start and end are detected automatically (by semicolon boundaries, ignoring comments as well as string and dollar-quoted literals); a prefix such as `RETURN QUERY` is trimmed back to the `SELECT`/`WITH`. If a **sub-select or a WITH clause is selected** instead, only the selection is used and not expanded to the whole statement. The `INTO` clause (including `INTO STRICT`) is removed automatically so that the statement runs on its own.
- **Variable prompt as a modal with a cache:** if the detected SELECT uses variables (values in comparisons, `IN`/`LIKE`/`BETWEEN` lists, positional parameters `$1` as well as `user`/`current_user`/`session_user`/`current_role`/`current_catalog`), a **modal dialog** opens in which a value can optionally be given for every variable. Empty fields leave the identifier unchanged; values are inserted verbatim (string literals therefore including their quotes). The values used last are **cached per variable name** and pre-filled the next time. The result is then shown in the **existing Data Viewer in a split editor** in read-only mode.
- **Copying numbers without thousands separators:** when copying from the Data Viewer, the thousands separators of numeric columns (a space by default) are removed — the displayed `9 999 999,99` becomes `9999999,99` in the clipboard. The decimal separator stays unchanged. For a multi-cell selection the cells are copied tab- and line-separated, whereby only numeric columns are normalised and text columns are taken over unchanged; selections without numeric cells behave like a normal copy.
- **Multi-line, formatted SELECT in the Data Viewer:** the query line of the Data Viewer is now a **multi-line input field** and shows the SELECT **formatted by default**: every top-level column stands indented on its own line, the clauses `FROM`/`JOIN`/`WHERE`/`GROUP BY`/`ORDER BY`/`LIMIT` and so on each start on a new line, and `WHERE` conditions are broken at top-level `AND`. The formatting is applied automatically when a table is opened, when an entry is picked from the query history and on filter, exclude and sort actions; a new **"Format"** button also formats hand-written SQL. Inside the field, **Enter** inserts a line break and **Ctrl/Cmd+Enter** runs the query. Strings, parentheses, function calls and comments are handled correctly; statements with comments, CTEs (`WITH`) or non-`SELECT` statements stay unchanged.


## 1.0.0

- **Drag a table into the editor:** a table from the table tree can now be dragged directly into any text editor. On drop, a picker appears with **Name only**, **Insert**, **Delete**, **Update**, **Select** (default) and **Join**; while navigating the picker, a live preview of the generated statement is shown. After confirmation the statement is inserted at the cursor position. All statements contain every column of the table and qualify the columns with a table alias (for example `SELECT lei.lei_id ... FROM leistungen lei`). The alias is derived from the part of the first column name before the first underscore (`lei_id` → `lei`) and falls back to the table name. A pencil button in the picker changes the alias per table; the choice is stored and reused next time.
- **Formatted SELECT:** the generated SELECT lists every column indented on its own line (the `SELECT` keyword and the `FROM` clause on separate lines).
- **DELETE with all columns in the WHERE clause:** the DELETE statement generated by drag & drop lists all columns of the table (qualified) in the WHERE clause, joined with `AND`.
- **UPDATE with type cast:** the UPDATE statement generated by drag & drop sets all columns and casts every value to the respective column type (for example `amount = NULL::numeric`).
- **INSERT with type cast:** the INSERT statement generated by drag & drop also casts every value to the respective column type (for example `NULL::numeric -- amount`).
- **Insert several tables as a JOIN SELECT:** several tables can be dragged into an editor together (with `Ctrl`/`Shift` multi-selection) from the tree view. A confirmation dialog opens that shows a `SELECT … FROM … JOIN …` across all tables with a live preview. The join conditions are pre-filled automatically from existing primary/foreign keys between the tables (tables without a relationship fall back to `CROSS JOIN`). In the dialog you can reorder the tables, rename aliases, choose the join type (INNER/LEFT/RIGHT/FULL/CROSS) and add, remove and edit join conditions. After confirmation the finished statement is inserted at the cursor position.

## 0.2.0

- Long context menus in the table view are now scrollable and are placed inside the viewport (they open upwards when there is not enough room below).
- The Data Viewer now shows a row number column (`#`) in front of the actions.
- The query history is now a searchable typeahead panel (wider, scrollable, with keyboard navigation and match highlighting) instead of a narrow dropdown.
- A right-click on a column header opens a context menu that sets, extends or removes the `ORDER BY` part of the current query (ASC/DESC, Replace/Add). If the column is already part of the `ORDER BY` clause, the menu additionally offers "Remove `col` from ORDER BY".
- Column filters (Enter) and "Add as Exact Match to Query" no longer overwrite a hand-written SELECT statement: existing `WHERE` conditions are kept, only an existing condition on the same column is replaced; all other conditions and `ORDER BY` stay untouched.
- When a linked table is opened (FK/PK/custom mapping) and for "Add as Exact Match to Query", the value is now only merged into the SELECT clause — the filter row stays empty instead of being pre-filled with the value.
- New **Modify History** panel below the Search panel: it persistently lists (up to 500 entries) every modifying statement that was executed (INSERT/UPDATE/DELETE/MERGE/TRUNCATE/CREATE/DROP/ALTER/GRANT/REVOKE/COMMENT/REFRESH/CALL) from table commits, from the query bar of the Data Viewer and from the SQL editor. Clicking an entry copies the SQL, "Clear" empties the history.
- The table view now shows in its toolbar which connection loaded the data that is currently visible (updated on every SELECT run). If the active connection changes afterwards, the display is marked as a warning.
- The "SQL Preview / Execute" dialog of the table view now shows both the current connection and the connection the data was loaded with. If the two differ, a clearly visible warning points out that the statement will run against the active connection.
- Custom column mappings are now shown in both directions: a mapping `A.col → B.col` also appears in table `B` as "Jump to A.col (reverse)" in the cell context menu and as a read-only entry with a "Reverse" badge in the manage dialog. Mappings are still edited and deleted on the original source table only.
- Custom mappings can now be **shared with colleagues through git**: every mapping has a scope, either "Personal" (as before, local per user in the VS Code globalState) or "Workspace" (stored in `.vscode/postgres-query-builder.mappings.json` inside the workspace and therefore committable). The mapping dialog has a checkbox "Share with workspace (commit to git)"; the manage dialog shows "Workspace"/"Personal" badges. The path to the workspace file is configurable through the setting `postgresQueryBuilder.customMappingsFile`; changes to the file (for example after a `git pull`) are picked up by a FileSystemWatcher and all open table views are refreshed. In addition, the commands "PostgreSQL: Export/Import Custom Column Mappings..." and "PostgreSQL: Open Workspace Custom Mappings File" are available for ad-hoc exchange.
- A new button **"Manage All Mappings..."** in the Search panel (and the command "PostgreSQL: Manage Custom Column Mappings...") opens a central management tab across _all_ mappings with a filter, multi-selection and bulk actions: share the selected mappings at once with "Move to Workspace (share)", make them private again with "Move to Personal", or delete several of them in one go. Quick selects for all personal or all workspace entries and a link that opens the workspace file are available as well.
- Individual mappings can now also be edited directly in the "Manage All Mappings..." tab: an "Edit" button per row opens a dialog for source/target columns, label, default flag, workspace sharing and conditions — changes are saved immediately in the respective store and refreshed in all open table views.
- **"Load More" now works for hand-written queries as well** from the query bar (for example after filtering or for custom SELECTs): the SQL is no longer bluntly extended with `LIMIT 50 OFFSET 0` and then disabled. Instead, a trailing `LIMIT`/`OFFSET` is stripped off (safely with respect to parentheses, strings and comments), the base SQL is remembered, and "Load More" appends further pages with a growing `OFFSET` to the rows already loaded. If the user wrote an explicit `LIMIT`/`OFFSET`, the button stays disabled as before.
- **`NULL` cells can now be edited directly:** clicking into a cell that shows `NULL` clears the placeholder right away so you can start typing. If the cell is left empty again, the value is stored as `NULL` as before and the `NULL` placeholder reappears.
- **Wider column field for mapping conditions:** in the mapping dialog (table view) and in the "Manage All Mappings" panel, the column picker for conditions is now much wider (instead of a fixed 60 px), so that long column names are fully readable. The operator selector stays narrow.
- **Single Record View:** a new detail view for a single row. It is opened either through the new eye icon (👁) in the action column of every row or through the context menu entry "View Full Record..." on a cell. The view lists all columns of the row one per line (column name with PK/FK badge and type on the left, a resizable textarea for the value on the right, optionally an FK jump button next to it), supports direct editing (empty = `NULL`, numeric columns are normalised), highlights changed fields with a "Reset" button and moves between the currently displayed rows (in the active filter/sort order) via "Prev/Next" buttons, `Alt+←` / `Alt+→` or the arrow keys. `Esc` closes the dialog. Changes go into the same pending-changes stack as in-place edits.
- **Single Record View — stable layout:** the dialog now has a fixed distance from the top (40 px) and a fixed height (`100vh − 80px`), so it no longer jumps vertically when switching between records of different size. When paging with Prev/Next (and after inline edits or a reset) the scroll position inside the dialog is kept instead of jumping back to the top every time.
- **New and duplicated rows now appear directly below the selected row** instead of at the end of the list. A row is selected by clicking anywhere in it (visible through a focus stripe on the left edge); "+ Insert Row" or the duplicate icon (⧉) append the new row right below it. If no row is selected, the new row goes to the top of the table. If the anchor row is hidden by a filter or sort, the new and duplicated rows belonging to it fall back to the end of the table so that they are not lost.
