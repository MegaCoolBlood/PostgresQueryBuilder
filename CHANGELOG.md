# Changelog

## 2.2.2

- **A cell whose value the column cannot store is outlined in red:** Until now a typo was only noticed when saving failed — the whole transaction was rejected and the change had to be found again. An edited cell is now checked as soon as it is left and marked with a red border and a tooltip explaining the problem (text in an `integer` column, `40000` in a `smallint`, six characters in a `varchar(5)`, a string that is not a timestamp, …). Saving stays blocked while any cell is marked, and the indicator next to the buttons shows how many values still need fixing.

    - **The rules come from the database, and so does the verdict for everything else.** Each result column now carries its real type including the modifier (`character varying(5)`, `numeric(10,2)`, `smallint`) as reported by `format_type()`, so numbers, ranges, text lengths, booleans and UUIDs are checked instantly in the grid without asking the server. Types whose text format only PostgreSQL can judge — timestamps, dates, intervals, JSON, enums, arrays, network and custom types — are handed to the database, which tries to cast the entered text and reports its own error message as the reason. That check runs once per edited cell (not per keystroke) and never writes anything.

- **One Data Viewer for both entry points — every feature is offered whenever it is possible:** Opening a table from the Table Explorer and running *"View Data"* on a `SELECT` used to open two different panels: the first was fully featured, the second was a read-only grid where editing, inserting, deleting, permanent constraints, column mappings and the relation metadata (primary keys, foreign-key navigation, referencing tables) were simply unavailable. Both now use the same panel and the same data path — the table view is just a panel that starts with the default query of that table — and what the panel offers is derived from the result itself instead of from how it was opened:

    - **Ad-hoc query results are editable.** PostgreSQL reports the source relation and column for every result field that maps 1:1 onto a table column, so the viewer resolves each column back to its origin (through aliases, joins and sub-selects) and writes changes back to the right table — column by column. Computed columns, aggregates and literals stay read-only, and a banner explains why when a result cannot be edited at all.
    - **Results joined from several tables can be edited in place.** Changes are grouped per source table and committed in a single transaction; the SQL preview shows exactly the statements that will run. Inserting and deleting rows stays reserved for results that come from exactly one table.
    - **Rows without a primary key are handled safely.** When the result carries every primary-key column, rows are matched by that key. Otherwise they are matched by all of their displayed values, a warning banner is shown, and each `UPDATE`/`DELETE` is verified to affect exactly one row — otherwise the whole transaction is rolled back and nothing is changed.
    - **Views, materialized views and results of unknown origin are recognized as read-only** instead of failing at commit time; constraints and column mappings still work when the result comes from a single relation.
    - **Table-bound features follow the query.** Running a query against a different table in an open panel switches the panel to that table: relation metadata, foreign-key navigation, permanent constraints and column mappings follow along. Conversely, a table panel showing an arbitrary query no longer pretends its rows still belong to the original table.
    - **Each panel has its own query history** instead of one shared bucket, the connection is established before a "View Data" panel opens (it previously opened against no connection), a failed query releases the loading spinner instead of leaving it running forever, and saving/discarding changes re-runs the query you are looking at instead of resetting the panel to `SELECT * FROM <table>`.
    - **The exact row count is only computed when it is useful.** The plain table view still shows *"Showing X of Y rows"*; for an arbitrary query the viewer shows how many rows are loaded and counts the full result only when you click the indicator — counting an expensive query is no longer forced on every run.

- **The Save preview shows the warnings and lets the statements be edited before they run:** The note about how rows are matched used to sit permanently in a banner above the grid, where it was easy to overlook and took up space while browsing. It is now shown where it matters — in the confirmation popup that opens when you press **Save**, together with a warning when the active connection is no longer the one the data was loaded from. The previewed statements are no longer a read-only text: they can be edited in place (**Reset** restores the generated version) and are then executed exactly as written, as a single transaction that either applies completely or not at all.

- **Column headers show at a glance how safely a column can be edited:**
 The header background now encodes where a column comes from — the **plain editor background** for a column that maps onto a table column whose rows are identified by a primary key (changes are written back exactly), a **greyed** shade for a column that maps onto a table column but whose rows can only be matched by all of their displayed values (a change is rejected unless it affects exactly one row), and a **blue tint** for a computed column, aggregate or literal that has no source table and therefore cannot be written back at all. The shades are mixed from the active colour theme, so they stay readable in light, dark and high-contrast themes. In a result joined from several tables each column is judged by its own table.

- **The "View Data" result no longer offers actions it cannot perform:** In the read-only custom-query view the **Constraints** button and the cell context-menu entries *"Create Custom Mapping…"* / *"Manage Mappings…"* were shown even though that panel has no table to attach them to — the messages they sent were dropped. Saving a permanent constraint there even overwrote the query bar with a nonsense `SELECT * FROM ""` and left the grid stuck on the loading spinner. All three affordances are now hidden whenever the view has no source table.

- **`INSERT` export from a "View Data" result uses a usable table name:** Because such a result has no source table, the INSERT export pre-filled the target with an empty quoted identifier and produced `INSERT INTO "" …`. It now falls back to `exported_data`, which can be edited in the export dialog as usual.

- **The `alwaysQuote` setting now also applies to the "View Data" result:** The custom-query panel never received the setting, so identifiers added by column filters, ORDER BY and the context-menu actions were quoted differently there than in a regular table view.

- **Export works again in a Data Viewer opened from a SELECT statement:** In the read-only custom-query view (the "View Data" command on a `SELECT`), the Export dialog was inert — clicking **Browse** opened no folder picker, the saved export defaults were never loaded, and **Export** itself did nothing at all. That panel has its own message handler which only knew about the query commands, so every export message from the webview was silently dropped. It now forwards `browseExportLocation`, `getExportDefaults`, `saveExportDefaults` and `exportData` to the same handlers the regular table view uses, so browsing for a folder, saving defaults and exporting the full result set behave identically in both views. If such a panel has no query text to export, the export now reports a clear error instead of trying to read from a non-existent table.

## 2.2.1

- **Files with Windows line endings (CRLF) are no longer skipped by the formatter:** The renderer joins its output with `\n`, so in a CRLF file the `\r` inside multi-line block comments and multi-line string literals was lost. Because such tokens are compared byte-for-byte, the safety net (correctly) rejected the result and reported *"formatting would have changed the code at token N: expected `/****…` but the formatted output had `/****…`"* — two comments that looked identical but differed in their line endings. Formatting now runs on LF-normalised text and restores the file's original CRLF endings afterwards.

- **Comment whitespace no longer disables formatting:** Trailing blanks inside a block comment (or after a `--` comment) were trimmed by the final formatting pass, which again changed a token that was compared verbatim. Comment tokens are now compared whitespace-insensitively — exactly as the safety net always documented — so re-indenting or trimming a comment is accepted, while any real change to a comment's text is still rejected.

- **Multi-line string literals inside a dollar-quoted body keep their payload:** When a `$body$ … $body$` block was re-indented, every physical line was shifted — including the interior lines of a multi-line string literal (e.g. a JSON template `'{\n  "messages": []\n}'`), which silently changed the string's content. Indentation is now only applied to lines that do not continue a string, dollar-quoted or quoted-identifier literal.

## 2.2.0

- **The row-count indicator now shows the query execution time:** Next to "Showing X of Y rows" (and "N rows returned" for custom queries), the Data Viewer now appends how long the SELECT took to run, e.g. `Showing 50 of 1240 rows · 18 ms` or `… · 1.23 s`. The time is measured on the server round-trip for both the standard table view and custom queries; sub-second times are shown in milliseconds, longer ones in seconds.

- **New "Load All" button next to "Load More":** The Data Viewer toolbar now has a "Load All" button that fetches every remaining row in a single request instead of one 50-row page at a time. It works for the standard table view (loads the rest up to the total row count) and for custom queries / filtered results (loads everything from the current position onward). Both pagination buttons disable once all rows are loaded.

- **Multi-line cell values no longer stretch the row; row height is now manually adjustable:** A cell containing a multi-line value previously made the whole row grow tall enough to show every line. Rows now stay a single line high by default and clip a multi-line value to its first line. To read the full text, drag the resize handle at the bottom edge of a row's number (`#`) cell to make just that row as tall as you need (bounded so it can never shrink below one line). Significant leading/trailing whitespace is still preserved.

- **Custom SELECTs now show their columns and filter row immediately:** Running a custom query previously left the header (and its per-column filter inputs, sort and context-menu actions) blank until the full result had been fetched. The extension now resolves the result columns up front with a fast zero-row describe probe (`SELECT * FROM (…) LIMIT 0`) and renders the header and filter row right away, while the actual rows are still loading. The probe is best-effort and only runs for a single-statement `SELECT`/`WITH` query; anything else falls back to the previous behavior of rendering columns once the result arrives.

- **Column headers in the Data Viewer now show the column comment as a tooltip:** When a column has a PostgreSQL comment (`COMMENT ON COLUMN …`), its header shows a small 🛈 indicator (right-aligned) and hovering the header reveals the comment text as a tooltip. Comments are read together with the column metadata (for tables and views alike) and default to none when a column is not documented. This also works for **custom SELECT** results: for each result column that maps back to a real table column, the comment is resolved from its source table via the field's table/column identity — computed columns and literals have no comment as expected.

- **Reordering columns now keeps a manually edited SELECT intact:** Previously, dragging a column header regenerated the query bar from scratch, which discarded manual edits — a column alias or a deleted column was lost, and once a custom query had been run the drag no longer changed the SELECT at all. Reordering now moves the matching column expression *inside the current query text*, so aliases, removed columns and any custom `WHERE`/`ORDER BY` (including a run custom query) are preserved and only the affected column changes position. The extension falls back to regenerating the default query only when the current text cannot be reordered by column index (for example a `SELECT *`).

- **Columns in the Data Viewer can now be reordered by drag-and-drop:** Grab a column header and drop it onto another column to move it to that position. The new order is applied to the grid immediately (header, filter row and all cells follow) and the SELECT column order in the query bar is updated to match — so the listed columns always mirror what you see on screen. Dragging shows a "grabbing" cursor and highlights the drop target; sorting (click) and the header context menu keep working as before.

- **The Data Viewer query bar now lists all columns instead of `SELECT *`:** When a table (or view) is opened in the Data Viewer from the Table Explorer, the query bar previously showed `SELECT * FROM <table>`. It now spells out every column by name — `SELECT col1, col2, … FROM <table>` — so the generated statement is explicit and ready to be trimmed or copied. Identifiers are quoted according to the same rules as the rest of the extension (and the `alwaysQuote` setting), and any permanent per-table `WHERE` constraints are still appended. While the column metadata is still loading the bar briefly falls back to `*`, and the query is refreshed to the full column list as soon as the columns are known.

## 2.1.5

- **Column filters now refine a custom query too:** In a custom-`SELECT` result the column filter row (and the cell context-menu actions "Add as Exact Match" / "Exclude this Value") did nothing, because they were gated on a known schema/table which a custom query does not have. Typing a term into a column filter and pressing Enter now merges the resulting condition into the `WHERE` clause of the query in the query bar and re-runs it, just like in a standard table view. Existing user-written clauses are preserved.

- **The connection badge in the Data Viewer is now clickable to switch connection:** The toolbar badge that shows which database the displayed data came from can now be clicked to open the connection picker and switch to another saved connection (the same picker used elsewhere). The badge shows a hover state and a "click to switch connection" hint, and when no connection is active yet it reads "Select connection…". Switching a connection updates every open Data Viewer as before.

- **Single Record View now respects read-only data views:** When the Data Viewer could not be edited (for example an ad-hoc custom `SELECT` result), the table grid correctly blocked edits, but opening a row in the Single Record View still let you type into the field textareas and register changes that could never be committed. The record dialog now marks all fields as `readonly` whenever the view is read-only (or the row is pending deletion), and `applyRecordEdit` ignores edits in read-only mode, so the two views behave consistently.

- **Reloading the Data Viewer now discards uncommitted edits instead of re-applying them to unrelated rows:** When a row was changed (but not saved) and the query was re-run — or the table was reloaded — the freshly fetched rows were displayed with the old pending edits still painted into the cells at the same 0-based row index, even though those values belonged to different (now replaced) rows. Any fresh first page or re-run query now resets all pending changes (cell edits, deletions, inserted and duplicated rows, and the row selection) so the grid always reflects the data actually returned by the database. "Load More" pagination still appends rows and keeps existing edits.

- **Leading/trailing spaces in Data Viewer cells are now shown and preserved:** Text values with significant whitespace (for example `" foo"`) were rendered without their leading spaces in the table view (the surrounding cell uses `white-space: nowrap`, which collapses them), even though the Single Record View showed them correctly. Worse, simply focusing such a cell and leaving it again trimmed the whitespace and flagged the cell as modified, silently altering the data on the next commit. Table cells now preserve their whitespace visually (`white-space: pre` on the editable cell content), and editing no longer trims leading/trailing spaces of text values — so clicking into and out of a cell no longer registers a phantom change. Numeric columns are still trimmed and reformatted as before.

## 2.1.4

- **A `SELECT` is no longer collapsed onto one line when a function call was deliberately split across lines with a compound argument:** A single-statement `SELECT` (for example the body of a `LANGUAGE sql` function) was treated as a "simple" `SELECT` and rendered on a single line even when the author had written a function call across several lines, such as `hashtext(COALESCE(a, '') || COALESCE('::' || b, ''))`. A function call whose single argument is a compound expression (it contains a top-level operator like `||`, `+`, …) and which the author split across multiple source lines now keeps its multi-line layout — the call wraps its argument onto its own indented line and the surrounding `SELECT` is no longer flattened. Calls written on one line, and multi-line calls whose argument is a single simple value (e.g. `foo(\n bar\n)`), still collapse as before.

- **Multi-line SQL statements inside a dollar-quoted `format()` template are now reformatted:** A dollar-quoted body was only reformatted when it contained a PL/pgSQL block (`BEGIN`/`DECLARE`). A dynamic-SQL template such as `format($query$ SELECT … FROM … WHERE x = %L $query$, …)` was therefore left with its original (often misaligned) indentation. The formatter now also recognises a dollar-quoted body whose first significant word starts a SQL statement (`SELECT`, `WITH`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`) and reformats it like the surrounding code, so the embedded query gets proper clause/column/`JOIN`/`WHERE` layout. For such a statement template the opening and closing `$query$` tags are placed on the same indentation level and the query itself is indented one level deeper; PL/pgSQL block bodies (`BEGIN`/`DECLARE`) keep their content on the same level as the tags as before. The detection only applies to multi-line bodies: a short single-line body (e.g. `AS $$ SELECT 1 $$`) and bodies that are plain text, JSON or regex patterns are still emitted verbatim.


- **`format()` placeholders (`%L`, `%I`, `%s`) are no longer broken apart when a dollar-quoted body is reformatted:** When a PL/pgSQL routine built dynamic SQL with `format($outer$ … WHERE x = %L … $outer$, …)`, the formatter recursed into the dollar-quoted body, tokenized `%L` as the modulo operator `%` followed by the identifier `L`, and inserted a space between them — turning `%L` into `% L`. Because `format()` treats `%L`/`%I`/`%s` as single placeholders, this silently changed the generated SQL (and the semantic safety net could not catch it, since `%L` and `% L` tokenize identically). The tokenizer now recognises a `%` immediately followed by a `format()` type character (`s`, `I` or `L`) as one indivisible token, so the placeholder is emitted verbatim. Modulo expressions written with spaces (`a % b`), `%TYPE`/`%ROWTYPE` attribute references, the literal `%%`, and a `%` applied to a longer identifier (`a % system`) are all unaffected.


- **`listThresholds.createFunction` (and `createProcedure`) now takes effect even when `preserveSingleLineRoutineHeaders` is enabled:** When a `createFunction` threshold of `"0, 1"` (or similar "always wrap") was configured in `.pgformat.json`, the CLI formatter left single-line function headers unchanged because the `preserveSingleLineRoutineHeaders: true` default short-circuited the threshold check before it could run. The fix makes the single-line shortcut yield to the threshold: if the parameter-list threshold demands multi-line output for the given number of parameters, the shortcut is skipped and the normal formatting logic expands the parameters to individual lines. Behaviour is unchanged for zero-parameter functions and for parameter counts that fall within the "follow source" band.

- **CLI and VSIX now share the same formatter defaults:** The code-level `DEFAULT_THRESHOLDS` in `plpgsqlFormatter.ts` were out of sync with the VS Code setting defaults defined in `package.json`. When no `.pgformat.json` was present the CLI used the old code defaults, producing different output than the VSIX extension for the same SQL. All thresholds are now aligned with the `package.json` values: `createFunction`/`createProcedure`/`createTable` default to `0, 1` (all parameters/columns wrap), `createType` to `1, 2`, `selectColumns` to `1, 3`, `insertColumns`/`arrayLiterals`/`inLists` to `2, 10`, `booleanGroups`/`joinConditions`/`ifConditions`/`caseConditions` to `1, 3`, `operatorChains` to `1, 6`, and `caseWhenThen`/`exceptionWhenThen`/`ifElse` to `0, 3`.

- **Configurable path to the formatter rules file (`postgresQueryBuilder.format.configPath`):** A new setting lets you point the extension at a formatter-rules JSON file anywhere, instead of only `.pgformat.json` in the workspace root. An absolute path is used as-is; a relative path is resolved against the workspace root; leaving it empty keeps the previous behaviour (`.pgformat.json` in the workspace root). The file uses the same schema as `.pgformat.json`, and its values still take precedence over personal VS Code settings.

## 2.1.3

- **Line comments directly attached to an operator (`||--`) no longer swallow the following code:** When a `--` comment followed an operator with no space (e.g. `TO_CHAR(…) || '.' ||-- P_TAG_KG`), the tokenizer mistook `||--` for a single operator, so the `--` never started a comment. As a result the code on the following lines was silently merged into the (non-)comment when formatting, effectively commenting out real code. In PostgreSQL `--` and `/*` always begin a comment and can never appear inside an operator; the tokenizer now stops an operator run before either marker, so the comment is recognised and the code is preserved.

- **Safety net now detects this class of corruption:** Because the previous tokenization produced no comment token at all, the formatter's semantic safety net could not see that code had been absorbed and let the bad output through. With the comment now tokenized correctly, the safety net again guarantees that formatting never turns live code into comment text.

## 2.1.2

- **Subqueries in SELECT column lists are now indented inside their parentheses:** Scalar subqueries placed as column expressions (e.g. `(SELECT COUNT(*) FROM … WHERE …) AS cnt`) were previously rendered with `SELECT`, `FROM` and `WHERE` at the same indentation level as the opening `(`. They are now indented one level deeper inside the parentheses, matching the established behaviour of `FROM (SELECT …)` subqueries. The fix applies at any nesting depth and inside PL/pgSQL blocks.

- **No spaces around PostgreSQL JSON path operators:** The operators `->`, `->>`, `#>` and `#>>` are now formatted without surrounding spaces (e.g. `v_json->>'key'` instead of `v_json ->> 'key'`), matching standard PostgreSQL usage. Chained access like `data->'user'->>'name'` is also kept compact.

- **Line comments on their own source line are no longer pulled onto the preceding expression line:** A `-- comment` that the author wrote on its own line (e.g. between two conditions inside an `AND (…)` group) was previously appended to the end of the expression above it. The newline before such a comment is now preserved so the comment keeps its own line.

## 2.1.1

- **Formatter no longer skips files that contain multi-line string literals with trailing whitespace:** The final formatting pass trimmed trailing spaces/tabs on *every* physical line, including lines *inside* a string literal (for example the body of a `format('… INSERT INTO … ')` call). Because a string literal must be preserved byte-for-byte, this altered the code and the safety net (correctly) rejected the result, silently disabling formatting for the whole file with a message like *"formatting would have changed the code at token N …"*. Trailing whitespace is now stripped only outside of string, dollar-quoted and quoted-identifier literals, so such files format normally again.

## 2.1.0

- **Repository-level formatter config (`.pgformat.json`):** Formatter settings can now be shared across a team via a `.pgformat.json` file in the workspace root. All keys mirror the VS Code setting names without the `postgresQueryBuilder.format.` prefix (e.g. `keywordCase`, `indentSize`, `listThresholds`). Values in the file take precedence over personal VS Code settings, so every developer formats consistently without touching their own `settings.json`. The file is optional; when absent the extension behaves as before.

- **Export formatter settings to `.pgformat.json`** (command *PostgreSQL Query Builder: Export Formatter Settings to .pgformat.json*): Creates or overwrites `.pgformat.json` in the workspace root with all current formatter settings (VS Code settings merged with any existing repo file). Asks for confirmation before overwriting an existing file, then opens the generated file in the editor.

- **Unified command category:** All extension commands now appear under the category `PostgreSQL Query Builder` in the Command Palette instead of the former `PostgreSQL`.

## 2.0.4

- **Neue Default-Aliase für Integer-Typen:** In `format.dataTypeAliases` sind jetzt zusätzlich `int2 -> smallint`, `int4 -> integer` und `int8 -> bigint` enthalten.

- **Mehrwort-Datentyp-Ersetzungen sind jetzt als Tabelle pflegbar:** Zusätzlich zum Schalter `postgresQueryBuilder.format.normalizeDataTypes` gibt es jetzt `postgresQueryBuilder.format.dataTypeAliases` als konfigurierbare Tabelle (Phrase -> Zieltyp), z. B. `"character varying" -> "varchar"`. Damit lassen sich die Ersetzungen individuell ergänzen/überschreiben, statt nur global ein-/auszuschalten.

- **Separate Einstellungen pro Single-Line-Sonderfall:** Statt eines gemeinsamen Schalters gibt es jetzt getrennte Optionen `postgresQueryBuilder.format.preserveSingleLineRoutineHeaders` und `postgresQueryBuilder.format.preserveSingleLineIfBlocks` (jeweils Standard: `true`). Damit lassen sich einzeilige Routine-Header und einzeilige einfache IF-Blöcke unabhängig voneinander ein-/ausschalten. Der bisherige Umbrella-Schalter `postgresQueryBuilder.format.preserveSingleLineSpecialCases` bleibt als veraltete Fallback-Option kompatibel.

- **Vollständig einzeilige `IF ... THEN ... END IF;`-Blöcke bleiben einzeilig:** Wenn ein kompletter IF-Block im Quelltext bereits in einer einzigen Zeile steht, bleibt er beim Formatieren nun ebenfalls in einer Zeile (analog zur Behandlung vollständig einzeiliger Routinen-Header).

- **`ROW(...)` wird jetzt wie eine Listen-Klammerung formatiert:** Der Row-Constructor wird nun in die Listen-Formatierung aufgenommen und nutzt dieselben Default-Schwellen wie Listen/Funktionsaufrufe. Damit bleibt z. B. `ROW(1, 2, 3)` einzeilig, während längere Varianten wie `ROW(1, 2, 3, 4, 5, 6)` standardmäßig mehrzeilig mit einem Element pro Zeile formatiert werden.

- **`JOIN ... ON` mit gemischtem `AND`/`OR` rückt `AND` jetzt ebenfalls eine Ebene tiefer ein:** In Bedingungen auf derselben Ebene mit gemischten `OR`-Alternativen und `AND`-Teilbedingungen gilt die Präzedenz-Einrückung jetzt auch im `JOIN ... ON`-Kontext. Dadurch hängen `AND`-Zeilen unter der jeweiligen `OR`-Alternative, statt auf derselben Ebene wie `OR` zu bleiben.

- **Präzedenz-Einrückung für gemischte `AND`/`OR` gilt jetzt in allen relevanten Bedingungskontexten:** Die Sonderbehandlung (bei `AND`+`OR` auf derselben Ebene werden `AND`-Zeilen eine Ebene tiefer als `OR` eingerückt) wird jetzt konsistent überall angewendet, wo solche Mischungen auftreten können, z. B. in `IF`/`ELSIF`-Bedingungen, `CASE WHEN`-Bedingungen und `JOIN ... ON`-Bedingungen.

## 2.0.3

- **Schwellenwert `multilineMin = 1` wird jetzt respektiert (einzelner Parameter kann erzwungen umbrochen werden):** Bisher hat `coerceFormatOptions` den zweiten Wert eines Schwellenwert-Paars auf **mindestens 2** hochgeklemmt, sodass z. B. `createFunction`/`createProcedure` = `"0, 1"` heimlich zu `"0, 2"` wurde – ein einzelner Parameter wurde dann bei einzeiliger Quelle doch nicht umbrochen. Die Untergrenze ist jetzt `1`, d. h. `"0, 1"` bewirkt zuverlässig, dass schon **ein** Parameter/Element umbrochen wird. Die shipped-Defaults für `createFunction` und `createProcedure` stehen jetzt auf `"0, 1"`.

- **Excel-artiges Markieren & Kopieren in der Datenansicht:** In der Tabellenansicht lässt sich jetzt ein Zellbereich über beliebig viele Spalten und Zeilen markieren – per Ziehen mit der Maus über die Zellen oder mit `Umschalt`+Klick zum Aufziehen. Mit `Strg`/`Cmd`+`C` wird der markierte Bereich als **Tab-getrennte Spalten und CRLF-getrennte Zeilen** kopiert und fügt sich direkt als Zellraster in Excel ein. Zahlenspalten werden dabei wie beim bestehenden Kopieren ohne Tausendertrennzeichen übernommen. Ein einfacher Klick bearbeitet/fokussiert weiterhin eine einzelne Zelle wie bisher; `Esc` hebt die Markierung auf.

- **Präzedenzbasierte Einrückung bei gemischten `AND`/`OR`-Bedingungen:** Enthält ein Bedingungs-Scope (eine `(…)`-Gruppe oder ein Klausel-Rumpf wie `WHERE`/`HAVING`) sowohl `AND` als auch `OR` auf derselben Ebene, werden die `AND`-Operatoren jetzt eine Ebene tiefer eingerückt als die `OR`-Operatoren – jede `OR`-Alternative steht auf der Basis-Ebene, ihre `AND`-Teilbedingungen hängen darunter. Scopes mit ausschließlich `AND` (oder ausschließlich `OR`) bleiben unverändert auf der Basis-Ebene. Der River-Stil eines `JOIN … ON` bleibt davon unberührt (rechtsbündige `ON`/`AND`/`OR`-Ausrichtung).

- **`MERGE`-Anweisungen werden jetzt formatiert:** `MERGE`, die zugehörigen `WHEN [NOT] MATCHED … THEN`-Klauseln und der abschließende `;` stehen auf einer Ebene; die `THEN`-Aktion (`UPDATE`/`INSERT`/`DELETE` samt `SET`/`VALUES`) wird eine Ebene tiefer eingerückt, und `USING (SELECT …)` sowie `INSERT (…) VALUES (…)` folgen den bestehenden Umbruchregeln. Wird die `WHEN`-Bedingung mehrzeilig (z. B. mit umbrochenem `AND (…)`), rückt das `THEN` – wie bei einem mehrzeiligen `IF` – auf eine eigene Zeile auf `WHEN`-Ebene. Beispiel: `MERGE` / `INTO … USING (` / … / `) t ON (…)` / `WHEN MATCHED THEN` / `··UPDATE` / `··SET` / … / `WHEN NOT MATCHED THEN` / `··INSERT (…)` / `··VALUES (…)` / `;`.

- **`GROUP BY`/`ORDER BY`-Umbruch in Cursor-`FOR`-Schleifen korrigiert:** In `FOR rec IN <Query> LOOP` lief die Längenerkennung der `GROUP BY`-/`ORDER BY`-Liste bisher über das `LOOP` hinaus in den Schleifenkörper – dessen Zeilenumbrüche wurden fälschlich als „mehrzeilige Liste" gewertet, sodass eine kurze einzeilige Liste umbrochen wurde. Die Liste endet jetzt korrekt am `LOOP`. Betroffen sind der Format-Befehl, der Dokument-/Bereichsformatierer und „Format on Save". Weicht etwas ab (z. B. weil ein Zeilenkommentar nachfolgenden Code verschluckt), wird die Formatierung verworfen und der **Originalcode unverändert** zurückgegeben. Damit kann ein Formatierungsfehler den Code im schlimmsten Fall nur unformatiert lassen, ihn aber niemals inhaltlich verändern. Neuer exportierter Helfer `sqlSemanticallyEqual(a, b)` für genau diesen Vergleich.

- **Verschachtelte `CASE`-Ausdrücke werden ebenfalls mehrzeilig formatiert:** Ein `CASE … END`, das als Ergebnis eines `WHEN … THEN`- oder `ELSE`-Zweigs eines äußeren `CASE`-Ausdrucks steht, wurde bisher auf eine einzige Zeile zusammengedrückt (alle `WHEN`-Zweige hintereinander). Jetzt wird ein solcher verschachtelter, im Quelltext mehrzeiliger `CASE` rekursiv als eigener Block gerendert – jeder `WHEN` auf einer eigenen, korrekt eingerückten Zeile, genau wie der äußere `CASE`.

- **Formatter verschluckt keinen Code mehr hinter Zeilenkommentaren:** Beim Formatieren von PL/pgSQL wurde ein Zeilenkommentar (`-- …`), der innerhalb eines Ausdrucks stand (z. B. nach einem `THEN`-Ergebnis in einem `CASE`-Ausdruck oder hinter einer Anweisung), inline ausgegeben, ohne anschließend einen Zeilenumbruch zu erzwingen. Dadurch landeten die nachfolgenden Tokens (z. B. der nächste `WHEN`-Zweig oder die nächste Anweisung) in derselben Zeile hinter dem `--` und wurden vom Kommentar „verschluckt" – das Ergebnis war ungültiger Code. Jetzt erzwingt der Formatter nach jedem inline ausgegebenen Zeilenkommentar einen Umbruch; der folgende Code bleibt erhalten.

- **„View Data from Select" zerstört Zeilenkommentare nicht mehr beim Entfernen von `INTO`:** Beim Entfernen der `INTO`-Zielklausel aus einem `SELECT … INTO … FROM …` wurde bisher der gesamte Whitespace der Anweisung auf einzelne Leerzeichen reduziert. Dadurch rückten Zeilenkommentare (`-- …`) und der nachfolgende Code in dieselbe Zeile, sodass der Kommentar den restlichen Code „verschluckte" – die ausgeführte Abfrage war fehlerhaft, und Variablen hinter einem Kommentar (z. B. `WHERE id = pi_xyz`) wurden nicht mehr erkannt. Jetzt bleiben Zeilenumbrüche und Kommentare erhalten; nur die `INTO`-Klausel selbst wird herausgeschnitten.

- **Textarea-Höhe im Single-Record-View bleibt erhalten:** Im Datenviewer-Einzelsatz-Dialog bleiben manuell vergrößerte Textfelder jetzt erhalten, wenn die Ansicht neu gerendert wird (z. B. beim Klick in ein anderes Textfeld) – zuvor wurden alle Textareas auf ihre Standardhöhe zurückgesetzt. Die gezogenen Höhen werden pro Spalte gemerkt, bis der Einzelsatz-Dialog geschlossen wird.

- **Selbst definierte Spalten-/CTE-Namen werden nicht mehr als Variablen abgefragt:** Beim Ausführen eines `SELECT` über „View Data from Select" wurden Bezeichner, die in einem Wert-Ausdruck stehen (z. B. nach `||` in `schema_name || '.' || function_name`), fälschlich als zu ersetzende Variablen erkannt – auch wenn es sich um vom Benutzer definierte Spalten-Aliase (`… AS function_name`) oder CTE-Namen (`WITH checks AS (…)`) handelte. Solche selbst definierten Namen werden jetzt erkannt und nicht mehr zur Ersetzung angeboten; echte PL/pgSQL-Variablen im selben Ausdruck werden weiterhin gefunden.

- **Fehlermeldung als Dialog im Datenviewer:** Schlägt eine im Datenviewer ausgeführte Abfrage (z. B. ein fehlerhaftes `SELECT`) fehl, wird die Fehlermeldung jetzt zusätzlich zur kleinen VS-Code-Benachrichtigung in einem deutlich sichtbaren Dialog direkt im Datenviewer angezeigt. Der Dialog zeigt den vollständigen Fehlertext und lässt sich über „Close", das ×-Symbol oder einen Klick auf den Hintergrund schließen.

- **Verbindungsabfrage, wenn keine Verbindung aktiv ist:** Wird für eine Aktion eine Datenbankverbindung benötigt (z. B. beim Ausführen eines `SELECT` im Datenviewer, beim Öffnen einer Tabelle oder beim Ausführen einer Custom Query) und ist aktuell keine Verbindung aktiv, wird der Benutzer jetzt aufgefordert, eine Verbindung auszuwählen (oder neu anzulegen), anstatt mit der Fehlermeldung „Not connected to a database" abzubrechen. Bricht der Benutzer die Auswahl ab, wird die Aktion still abgebrochen.

- **Navigation über umgekehrte Custom Mappings berücksichtigt die Bedingungen:** Beim Springen (Rechtsklick → „Jump to … (reverse)") über ein umgekehrtes Custom Mapping werden jetzt die Bedingungen des ursprünglichen Mappings in die `WHERE`-Klausel der Zieltabelle übernommen. Beispiel: Bei einem Mapping von Tabelle A nach B über `a.id = b.id` mit der Bedingung `type = 'A'` erzeugt die Rückwärts-Navigation von B (id = 2) nach A jetzt `SELECT * FROM a WHERE id = 2 AND type = 'A'` statt nur `WHERE id = 2`. `LIKE`/`ILIKE`-Bedingungen werden dabei als „enthält"-Vergleich (`%wert%`) übernommen, passend zur Auswertung der Mapping-Bedingungen.

- **`JOIN … ON …`-Bedingungen mit eigenem `ON` und ausgerichteten Schlüsselwörtern:** Erstreckt sich die `ON`-Bedingung eines `JOIN` über mehrere Zeilen (gemäß `joinConditions`-Schwellwert), steht `ON` jetzt in einer eigenen Zeile direkt unter dem `JOIN`. Die Schlüsselwörter `ON`, `AND` und `OR` werden dabei rechtsbündig (River-Stil) ausgerichtet, sodass die Bedingungen darunter exakt fluchten:

  ```sql
  JOIN bos_t_kal_hours btkh
     ON btkh.kal_tag = let.let_kal_tag
    AND lze.lze_menge = btkh.p_worktimetarget
    AND btkh.session_id = p_websessionid
  ```

  Ein `JOIN` mit nur einer Bedingung bleibt weiterhin einzeilig (`JOIN u ON t.a = u.a`).

Jede Zeile enthält das Paar `"inlineMax, multilineMin"`: bei **höchstens** `inlineMax` Elementen immer einzeilig, bei **mindestens** `multilineMin` Elementen immer mehrzeilig, dazwischen wie im Quelltext (einzeilig bleibt einzeilig, mehrzeilig bleibt mehrzeilig). Die Liste umfasst jetzt folgende Konstrukte (Standardwerte in Klammern):
  - `createFunction` – `CREATE FUNCTION`-Parameterliste (`1, 4`)
  - `createProcedure` – `CREATE PROCEDURE`-Parameterliste (`1, 4`)
  - `createType` – `CREATE TYPE`-Attributliste (zusammengesetzte Typen sowie `ENUM`/`RANGE`) (`1, 4`)
  - `createTable` – `CREATE TABLE`-Spaltenliste (`1, 4`)
  - `returnsTable` – `RETURNS TABLE(…)`-Spaltenliste einer `CREATE FUNCTION` (`1, 4`)
  - `functionCall` – Funktions-/Prozeduraufruf-Argumentliste (`1, 4`)
  - `selectColumns` – `SELECT`-Spalten- und `INTO`-Zielliste (`1, 2`)
  - `fromTables` – `FROM`-Tabellenliste im Komma-Stil (`FROM a, b, c`) (`1, 4`)
  - `insertColumns` – `INSERT`-Spalten- und `VALUES`-Liste (`2, 6`)
  - `arrayLiterals` – `ARRAY[…]`-Literale inkl. verschachtelter Element-Arrays (`4, 12`)
  - `inLists` – `IN (…)`-Wertelisten (`4, 12`)
  - `booleanGroups` – boolesche Gruppen in Klammern (`(a AND b OR c)`) (`1, 2`)
  - `joinConditions` – `JOIN … ON … AND …`-Bedingungen (`1, 2`)
  - `ifConditions` – `IF`-/`ELSIF`-Bedingungen (`1, 2`)
  - `caseConditions` – `CASE … WHEN`-Bedingungen (`AND`/`OR` innerhalb einer `WHEN`-Bedingung) (`1, 2`)
  - `operatorChains` – Operator-Ketten (`+`, `-`, `*`, `/`, `||`) in einem Ausdruck (`1, 8`)
  - `caseWhenThen` – Zusammenklappen eines `CASE … WHEN … THEN`-Blocks (nur `inlineMax`; `0` = nie zusammenklappen)
  - `exceptionWhenThen` – Zusammenklappen eines `EXCEPTION WHEN … THEN`-Blocks (nur `inlineMax`; `0` = nie zusammenklappen)
  - `ifElse` – Zusammenklappen eines `IF … ELSE … END IF`-Blocks (nur `inlineMax`; `0` = nie zusammenklappen)
- **`CREATE TABLE`-Spaltenliste umbrechen:** Die Spaltenliste eines `CREATE TABLE … (…)` wird nach den `createTable`-Schwellwerten (Standard `1, 4`) umgebrochen.
- **`RETURNS TABLE(…)`-Spaltenliste umbrechen:** Die Spaltenliste eines `RETURNS TABLE(…)` einer `CREATE FUNCTION` wird nach den `returnsTable`-Schwellwerten (Standard `1, 4`) wie eine Parameterliste umgebrochen (eine Spalte je Zeile, schließende Klammer auf eigener Zeile); zwischen `TABLE` und der Klammer steht dabei kein Leerzeichen.
- **`SELECT`-Spalten und `FROM`-Tabellenliste nach Schwellwert:** Die `SELECT`-/`INTO`-Liste (`selectColumns`, Standard `1, 2`) und die kommagetrennte `FROM`-Tabellenliste im alten Stil (`fromTables`, Standard `1, 4`) richten sich jetzt nach ihren eigenen Schwellwerten statt allein nach der Quelltext-Anordnung.
- **`ARRAY[…]`-Literale umbrechen:** Element-Listen von `ARRAY[…]`-Literalen (inkl. verschachtelter Arrays) werden nach den `arrayLiterals`-Schwellwerten (Standard `4, 12`) umgebrochen; Index-Zugriffe (`arr[i]`) bleiben weiterhin einzeilig. (Hinweis: eine einfache `SELECT`-Anweisung mit nur einem ARRAY-Wert bleibt durch `simpleSelectSingleLine` weiterhin einzeilig.)
- **`IN (…)`-Wertelisten umbrechen:** `IN`-Wertelisten werden nach den `inLists`-Schwellwerten (Standard `4, 12`) umgebrochen.
- **Bedingungen je Konstrukt steuerbar:** Das Umbrechen von `AND`/`OR` lässt sich getrennt für `JOIN … ON …` (`joinConditions`), `IF`/`ELSIF` (`ifConditions`) und `CASE … WHEN` (`caseConditions`) konfigurieren. Mit den Standardwerten (`1, 2`) bleibt das bisherige Verhalten erhalten (ab zwei Teilbedingungen je `AND`/`OR` in einer eigenen Zeile); höhere Schwellwerte halten kurze Bedingungen einzeilig.
- **Lange Operator-Ketten umbrechen:** Ein Ausdruck, der mit `+`, `-`, `*`, `/` oder `||` viele Operanden verkettet (z. B. eine lange Summe von `CASE … END`), wird nach den `operatorChains`-Schwellwerten (Standard `1, 8`) umgebrochen — jeder Operator beginnt eine eigene, eingerückte Zeile (operator-führend), analog zu booleschen Gruppen. Ein einzelnes `CASE … END` zählt dabei als ein Operand.
- **`INSERT`-Spalten- und `VALUES`-Liste einheitlich formatieren:** Spaltenliste und `VALUES`-Liste eines `INSERT` werden gemeinsam entschieden und immer gleich umbrochen — nach den `insertColumns`-Schwellwerten (Standard `2, 6`).
- **Strukturblöcke zusammenklappen (`caseWhenThen`, `exceptionWhenThen`, `ifElse`):** Kleine Strukturblöcke lassen sich auf eine Zeile zusammenklappen. Ein Block wird einzeilig dargestellt, wenn die Anzahl seiner Anweisungen (`;`) kleiner oder gleich `inlineMax` ist und der Rumpf weder Kommentare noch verschachtelte Blöcke (`IF`/`CASE`/`LOOP`/`BEGIN`/`DECLARE`/`EXCEPTION`) enthält:
  - `ifElse` – `IF … THEN … [ELSE …] END IF;` (z. B. `IF a THEN x := 1; END IF;`)
  - `caseWhenThen` – `CASE … WHEN … THEN … END CASE;`
  - `exceptionWhenThen` – `EXCEPTION WHEN … THEN …;` (das `END` des umschließenden `BEGIN` bleibt in eigener Zeile)
  
  Mit dem Standard `inlineMax = 0` wird nie zusammengeklappt (das bisherige mehrzeilige Verhalten bleibt erhalten); ab `inlineMax ≥ 1` werden entsprechend kleine Blöcke einzeilig dargestellt.

- **Konfigurierbarer PL/pgSQL-Formatierer:** Neuer Formatierer für SQL- und PL/pgSQL-Code, der über die VS-Code-Standardfunktion **„Format Document"** (`Shift+Alt+F`), den Befehl **„PostgreSQL: Format PL/pgSQL"** (Command Palette und Editor-Kontextmenü), einen **„Format PL/pgSQL"**-Button im SQL-Editor sowie optional beim Speichern erreichbar ist. Der Formatierer rückt PL/pgSQL-Blöcke (`DECLARE`/`BEGIN`/`END`, `IF`/`ELSIF`/`ELSE`, `LOOP`) ein, bricht SQL-Klauseln (`SELECT`/`FROM`/`WHERE`/`JOIN`/`ORDER BY` …) und Spaltenlisten strukturiert um, vereinheitlicht die Schreibweise von Schlüsselwörtern und Datentypen und behält dabei Zeichenketten, Kommentare und vom Benutzer gesetzte Leerzeilen unverändert bei. `CASE`-Ausdrücke werden korrekt als Ausdruck behandelt (kein fälschliches Aufbrechen an `ELSE`/`END`); Funktionsrümpfe in `$$ … $$` werden rekursiv formatiert. Die Ausgabe ist eine reine Neuformatierung der vorhandenen Token, sodass keine Bestandteile einer Anweisung verloren gehen, und sie ist idempotent (erneutes Formatieren ändert nichts mehr).
  - Konfigurierbar über folgende Einstellungen (Standardwerte in Klammern): `postgresQueryBuilder.format.enable` (an), `postgresQueryBuilder.format.formatOnSave` (aus), `postgresQueryBuilder.format.keywordCase` (`upper`), `postgresQueryBuilder.format.identifierCase` (`preserve`), `postgresQueryBuilder.format.dataTypeCase` (`upper`), `postgresQueryBuilder.format.indentStyle` (`space`), `postgresQueryBuilder.format.indentSize` (`2`) und `postgresQueryBuilder.format.commaStyle` (`trailing`). Der Formatierer ist für die Sprach-IDs `sql`, `postgres` und `pgsql` registriert.
  - **Verbesserungen am Formatierer:**
    - **Routinen-Header (`CREATE FUNCTION`/`PROCEDURE`):** Der Kopf wird jetzt strukturiert formatiert — Parameterlisten werden je nach Anzahl umgebrochen (siehe `format.listThresholds`, Eintrag `functionCall`), `RETURNS …` bleibt auf der Zeile der schließenden Klammer, Charakteristika (`LANGUAGE`, `STABLE`, `SECURITY DEFINER`, `SET …` …) stehen je in einer eigenen, eingerückten Zeile, `AS` beginnt in Spalte 0, und der Rumpf (`DECLARE`/`BEGIN`/`END`) ist nicht zusätzlich eingerückt.
    - **`EXCEPTION … WHEN … THEN`-Blöcke** in PL/pgSQL werden jetzt korrekt umgebrochen und eingerückt (`EXCEPTION` auf `BEGIN`-Ebene, `WHEN` eine Ebene tiefer, der Handler-Rumpf nochmals eine Ebene tiefer).
    - **`IF [NOT] EXISTS`** (z. B. `CREATE SCHEMA IF NOT EXISTS …`, `DROP TABLE IF EXISTS …`) wird nicht mehr fälschlich als PL/pgSQL-`IF`-Block behandelt und umgebrochen.
    - **Typmodifizierer** wie `VARCHAR(500)` oder `NUMERIC(10,2)` behalten ihre Klammer ohne eingefügtes Leerzeichen.
    - **Klauselwörter innerhalb von Funktionsaufrufen** (z. B. `substring(… FROM 1 FOR 500)`) werden nicht mehr fälschlich als SQL-Klauseln umgebrochen; das Umbrechen von `SELECT`/`FROM`/`WHERE`/… greift nur noch im echten SQL-Kontext (Unterabfragen).
    - **`ARRAY[…]`-Literale** bleiben einzeilig (Kommas innerhalb der eckigen Klammern lösen keinen Listenumbruch aus).
    - **Argument-/Parameterumbruch konfigurierbar:** Aufruf- und Parameterlisten werden bei höchstens `inlineMax` Argumenten immer einzeilig gehalten und ab `multilineMin` Argumenten immer mehrzeilig umgebrochen; dazwischen bleibt die im Quelltext gewählte Anordnung erhalten (Eintrag `functionCall` in `format.listThresholds`).
    - **Leerzeilen 1:1 beibehalten:** Vom Benutzer gesetzte Leerzeilen werden standardmäßig exakt beibehalten (`blankLines: preserve`); alternativ lassen sie sich auf maximal eine zusammenfassen (`collapse`).
    - **Einfache `SELECT`-Anweisungen** (eine Spalte, höchstens eine Tabelle, höchstens eine `WHERE`-Bedingung, kein `JOIN`/`GROUP`/`ORDER`) bleiben standardmäßig auf einer Zeile (`simpleSelectSingleLine`).
    - **Einzeilig geschriebene Funktionen/Prozeduren bleiben einzeilig:** Ist eine `CREATE [OR REPLACE] FUNCTION`/`PROCEDURE`-Anweisung im Quelltext vollständig auf einer einzigen Zeile geschrieben (inkl. Rumpf in `$$ … $$`), wird sie nicht mehr in den mehrzeiligen Routinen-Header aufgebrochen, sondern bleibt einzeilig (Schlüsselwörter/Datentypen werden weiterhin vereinheitlicht, der Rumpf bleibt unverändert). Beispiel: `CREATE FUNCTION pk.g_pair() RETURNS VARCHAR LANGUAGE SQL IMMUTABLE AS $$ SELECT 'X'; $$;` bleibt so erhalten. Über mehrere Zeilen geschriebene Routinen werden weiterhin strukturiert formatiert.
    - **`SELECT`-/`INTO`-Listen: ein Wert bleibt in der Zeile, mehrere werden umgebrochen:** Wird nur ein einzelner Ausdruck selektiert, steht er jetzt direkt hinter dem `SELECT`-Schlüsselwort (`SELECT 1`); bei mehreren Ausdrücken wird die Liste wie bisher auf mehrere Zeilen aufgeteilt. Dasselbe gilt für die `INTO`-Zielliste in `SELECT … INTO`. `INTO` (z. B. `INTO STRICT v_dummy`) beginnt nun grundsätzlich eine eigene Zeile (nur `INSERT INTO …` bleibt einzeilig).
    - **`AND`-Bedingungen je in eigener, eingerückter Zeile:** In `WHERE`-/`HAVING`-/`ON`-Bedingungen beginnt jedes top-level `AND` jetzt eine neue, um eine Ebene tiefer eingerückte Zeile. Ausnahme ist das zu einem `BETWEEN` gehörende `AND` — `… AND x BETWEEN y AND z` bleibt zusammen in einer Zeile.
    - **`%TYPE`/`%ROWTYPE` ohne Leerzeichen:** Attributtyp-Verweise wie `bos_mitarbeiter%ROWTYPE` oder `t.c%TYPE` werden jetzt ohne Leerzeichen um das `%` direkt an den Namen angehängt (`v_mitRec bos_mitarbeiter%ROWTYPE;`). Das Modulo-`%` als Operator (`a % b`) bleibt davon unberührt und behält seine Leerzeichen.
    - **Typnamen normalisieren:** Ausführliche, mehrteilige Typbezeichnungen werden beim Formatieren auf ihre Kurzform vereinheitlicht — `character varying` → `varchar`, `bit varying` → `varbit`, `timestamp without time zone` → `timestamp`, `timestamp with time zone` → `timestamptz`, `time without time zone` → `time`, `time with time zone` → `timetz` (Typmodifizierer wie `(500)` bleiben erhalten, z. B. `character varying(500)` → `varchar(500)`). Steuerbar über die neue Einstellung `postgresQueryBuilder.format.normalizeDataTypes` (Standard: an).
    - **Nachgestellte Zeilenkommentare bleiben in der Zeile:** Ein `--`-Kommentar, der im Quelltext am Ende einer Zeile steht (z. B. hinter dem abschließenden `;` einer einzeiligen Funktion), wird nicht mehr in eine eigene Zeile verschoben, sondern bleibt an dieser Zeile hängen. Kommentare, die bereits in einer eigenen Zeile stehen, behalten ihre eigene Zeile.
    - **Leerzeilen vor Anweisungen wie `CREATE`/`UPDATE`/`INSERT` bleiben erhalten:** Vom Benutzer gesetzte Leerzeilen vor einer Anweisung, die nicht mit einem Klausel-Schlüsselwort beginnt (z. B. mehrere leere Zeilen zwischen zwei `CREATE FUNCTION`-Definitionen), wurden bisher entfernt. Sie werden nun — wie bei den übrigen Klauseln — 1:1 beibehalten.
    - **Leerzeilen vor Kommentaren bleiben erhalten:** Eine vom Benutzer gesetzte Leerzeile direkt vor einem eigenständigen `--`-Kommentar (z. B. vor einer Abschnittsüberschrift im `DECLARE`-Block) wurde bisher entfernt; sie wird jetzt beibehalten.
    - **Präfix-Stringliterale wie `E'…'` bleiben unverändert:** Escape-/Bit-/Hex-/Unicode-Stringliterale (`E'\n'`, `B'1010'`, `X'1f'`, `U&'\0041'` sowie ihre Kleinschreibung) werden jetzt als ein Token erkannt. Bisher wurde der Präfix vom Stringinhalt getrennt (`E '\n'`), was zu fehlerhaftem SQL führte.
    - **`CASE`-Ausdrücke strukturiert formatieren:** Ein `CASE`-Ausdruck, der im Quelltext vollständig auf einer Zeile steht, bleibt einzeilig (`CASE WHEN a AND b THEN 1 ELSE 0 END`). Ein über mehrere Zeilen geschriebener `CASE`-Ausdruck wird jetzt strukturiert: Jedes `WHEN` (und `ELSE`/`END`) beginnt eine eigene Zeile, `WHEN`/`ELSE` eine Ebene tiefer als `CASE`, `END` wieder auf `CASE`-Ebene. Ist eine `WHEN … THEN …`-Klausel im Quelltext einzeilig, bleibt sie einzeilig; erstreckt sie sich über mehrere Zeilen, beginnt das Ergebnis nach `THEN` in einer eigenen, tiefer eingerückten Zeile. Besteht die Bedingung eines `WHEN` aus mehreren top-level mit `AND`/`OR` verknüpften Teilbedingungen, wird jede weitere Teilbedingung in eine eigene, eingerückte Zeile umgebrochen, `THEN` steht dann allein in einer Zeile und das Ergebnis darunter — das zu einem `BETWEEN` gehörende `AND` bleibt dabei in der Zeile. Die `CASE`-Anweisungsform (`CASE … END CASE;` mit Anweisungen wie `IF … END IF;` im Rumpf) wird davon nicht erfasst und korrekt erkannt — verschachtelte `IF`/`LOOP`/`BEGIN`-Blöcke werden beim Suchen des zugehörigen `END` mitgezählt, sodass der Anweisungsrumpf nicht mehr fälschlich in eine Zeile gezogen (und hinter einem Zeilenkommentar „auskommentiert") wird. Die `CASE`-Anweisungsform wird außerdem strukturiert eingerückt: `CASE`/`END CASE` stehen auf Blockebene, jedes `WHEN`/`ELSE` eine Ebene tiefer, und der jeweilige Anweisungsrumpf (Zuweisungen, verschachtelte `IF`/`LOOP`-Blöcke …) beginnt in einer neuen Zeile nach `THEN` und wird nochmals eine Ebene tiefer eingerückt (Leerzeilen und nachgestellte Kommentare bleiben erhalten).
    - **`FOR … IN <SELECT …> LOOP`-Schleifen strukturiert formatieren:** Bei einer Schleife über eine Abfrage steht `FOR … IN` weiterhin in einer eigenen Zeile, die Abfrage (`SELECT`/`FROM`/`WHERE`/…) wird jetzt eine Ebene tiefer eingerückt, und das `LOOP`-Schlüsselwort beginnt eine eigene Zeile auf Höhe des `FOR` (statt an die letzte Abfragezeile angehängt zu werden). Der Schleifenrumpf wird wie gehabt eingerückt. Einfache Schleifenköpfe (`FOR i IN 1..10 LOOP`, `WHILE … LOOP`) bleiben dagegen kompakt auf einer Zeile.
    - **Geklammerte Boolean-Gruppen umbrechen:** Eine geklammerte Bedingung, die auf oberster Ebene mit `AND`/`OR` verknüpft ist (z. B. `AND (a <> 1 OR b IS NOT NULL)`), wird jetzt mehrzeilig formatiert: Die öffnende Klammer bleibt am Zeilenende, jeder Operand und jedes `AND`/`OR` stehen auf einer eigenen, eine Ebene tiefer eingerückten Zeile, und die schließende Klammer wird wieder ausgerückt. `OR` beginnt – wie schon `AND` – innerhalb von Bedingungen eine eigene Zeile (außer in `CREATE OR REPLACE`). Reine Gruppen ohne Boolean-Verknüpfung (`(a + b)`, `IN (1, 2, 3)`, `(x BETWEEN 1 AND 5)`) bleiben einzeilig.
    - **Mehrfache Formatierungsdurchläufe:** Der Formatierer wird jetzt bis zu zehnmal auf sein eigenes Ergebnis angewendet, bis sich nichts mehr ändert. Dadurch werden auch neu entstandene Zeilenumbrüche (etwa in verschachtelten Boolean-Gruppen) sauber nachgerückt, und das Ergebnis ist idempotent.
    - **`THEN` bei mehrzeiligen `IF`/`ELSIF`-Bedingungen:** Wird eine `IF`- oder `ELSIF`-Bedingung durch `AND`/`OR` über mehrere Zeilen umbrochen, steht das `THEN` jetzt in einer eigenen Zeile auf Höhe des `IF`/`ELSIF` (statt an die letzte Bedingungszeile angehängt zu werden). Einzeilige Bedingungen behalten `THEN` weiterhin am Zeilenende.
  - **Neue Einstellungen (Standardwerte in Klammern):** `postgresQueryBuilder.format.blankLines` (`preserve`), `postgresQueryBuilder.format.simpleSelectSingleLine` (`true`), `postgresQueryBuilder.format.listThresholds` (Tabelle pro Konstrukt) und `postgresQueryBuilder.format.normalizeDataTypes` (`true`).

Dadurch lässt sich z. B. der **„Constraints"**-Dialog schon öffnen und eine dauerhafte Bedingung hinzufügen, bevor die Daten vollständig geladen sind. B. `CURRENT_TIMESTAMP BETWEEN valid_from AND valid_to`, um stets nur die aktuell gültigen Datensätze anzuzeigen). Der Bedingungs-Editor nutzt **dasselbe Design wie „+ Add fixed condition" im JOIN-Dialog**: Jede Bedingung besteht aus linkem Operand, Operator und rechtem Operand; Operanden werden entweder per Dropdown als **Spalte** der Tabelle oder als **freier Wert/Ausdruck** (z. B. `'TGB'` oder `CURRENT_TIMESTAMP`) eingegeben. Als Operatoren stehen `=`, `<>`, `<`, `<=`, `>`, `>=`, `LIKE`, `ILIKE`, `BETWEEN` (zwei rechte Operanden) sowie `IS NULL`/`IS NOT NULL` (ohne rechten Operanden) zur Verfügung. Eine Live-Vorschau zeigt die resultierende Abfrage; mit **„Save & Apply"** werden die Bedingungen dauerhaft gespeichert und die Ansicht sofort neu geladen. Die Bedingungen werden strukturiert im globalen Zustand der Erweiterung pro `schema.tabelle` abgelegt und gelten weiterhin als reguläre `WHERE`-Klausel, sodass die Datensätze in der Datenansicht bearbeitbar bleiben (Primärschlüssel-/Fremdschlüssel-Metadaten werden weiterhin geladen).
- **„View Data": `IS NULL` / `IS NOT NULL`-Filter per Spalten-Rechtsklick:** Im Kontextmenü einer Spaltenüberschrift in der Datenansicht gibt es jetzt die Einträge **„Add `<Spalte>` IS NULL to WHERE"** und **„Add `<Spalte>` IS NOT NULL to WHERE"**. Damit lässt sich mit einem Klick eine `IS NULL`- bzw. `IS NOT NULL`-Bedingung für die gewählte Spalte zur aktuellen `WHERE`-Klausel hinzufügen; eine bereits bestehende Bedingung auf derselben Spalte wird dabei ersetzt. Die geänderte Abfrage wird sofort ausgeführt.
- **Custom Mapping: Mehrspaltige Verknüpfung (zusammengesetzter Schlüssel):** Benutzerdefinierte Spalten-Verknüpfungen (Custom Mappings) können jetzt mehrere Spaltenpaare abgleichen, um zusammengesetzte Schlüssel (Composite Keys) abzubilden, z. B. `a.order_id = b.order_id AND a.tenant_id = b.tenant_id`. Im Mapping-Dialog gibt es dazu den neuen Abschnitt **„Additional column matches"** mit dem Button **„+ Add column match"**, der dieselbe Bedienlogik wie der Build-JOIN-Dialog verwendet: Quell-Spalte per Dropdown auswählen und Ziel-Spalte per Typeahead eingeben; alle Paare werden mit `AND` kombiniert. Beim Ableiten von JOINs erzeugt jedes Spaltenpaar eine eigene ON-Bedingung, sodass im JOIN-Dialog automatisch die vollständige zusammengesetzte Verknüpfung vorbelegt wird. Umgekehrte (reverse) Mappings tauschen Quell- und Zielspalte aller Paare korrekt. Bestehende einspaltige Mappings bleiben unverändert kompatibel.
- **„View Data": UPDATE/DELETE für Tabellen ohne Primärschlüssel:** Bei Tabellen ohne Primärschlüssel schlugen Änderungen und Löschungen in der Datenansicht bisher fehl bzw. erzeugten eine leere `WHERE`-Klausel. Jetzt wird die betroffene Zeile in diesem Fall über **alle Spaltenwerte** identifiziert (Vollzeilen-Abgleich), sodass `UPDATE`- und `DELETE`-Anweisungen die richtige Zeile treffen. `NULL`-Werte in der Identifizierung werden korrekt als `IS NULL` (statt `= NULL`) abgebildet — sowohl in der SQL-Vorschau als auch beim parametrisierten Commit. Zur Sicherheit wird eine Anweisung mit komplett leerer `WHERE`-Klausel abgelehnt (mit Rollback der Transaktion), damit niemals versehentlich alle Zeilen geändert oder gelöscht werden. Tabellen mit Primärschlüssel verhalten sich unverändert (Identifizierung weiterhin nur über die PK-Spalten).
- **JOIN-Dialog: dieselbe Tabelle mehrfach hinzufügbar (Self-Join):** Im JOIN-Dialog kann jetzt dieselbe Tabelle mehrmals mit jeweils eigenem Alias und eigener Join-Bedingung hinzugefügt werden (z. B. für Self-Joins wie `employees e LEFT JOIN employees m ON m.id = e.mgr_id`). Beim Hinzufügen über „+ Add tables…" werden bereits im Join enthaltene Tabellen nicht mehr ausgefiltert, sondern in der Auswahlliste mit dem Hinweis „already in join — adds another instance" angezeigt. Jede hinzugefügte Instanz erhält einen eindeutigen Alias und wird als eigenständige Tabelle behandelt; standardmäßig wird die zusätzliche Instanz als `CROSS JOIN` eingefügt, sodass die Join-Bedingung anschließend frei gegen eine beliebige frühere Tabelle (auch eine andere Instanz derselben Tabelle) gesetzt werden kann.
- **JOIN-Dialog: Auto-Vorbelegung der ON-Bedingungen auch beim erneuten/mehrfachen Hinzufügen:** Eine erneut oder mehrfach hinzugefügte Tabelle erhält jetzt dieselben automatisch abgeleiteten Join-Bedingungen wie beim ersten Hinzufügen. Die Zuordnung erfolgt nun durchgängig über die Tabellen-/Spaltennamen aus den Fremdschlüssel- und Custom-Mapping-Kanten (statt über einen einzelnen Tabellenindex), sodass auch eine zweite Instanz derselben Tabelle korrekt mit der passenden früheren Tabelle (inkl. Self-Join über selbstreferenzierende Fremdschlüssel) verbunden wird.
- **JOIN-Dialog: Alias-Nummerierung gibt freigewordene Suffixe wieder frei:** Wird eine zuvor hinzugefügte Tabelle (z. B. mit Alias `tabelle2`) wieder entfernt und erneut hinzugefügt, erhält sie wieder `tabelle2` statt fortlaufend `tabelle3`. Die Eindeutigkeitsprüfung berücksichtigt jetzt nur noch die Aliase der aktuell sichtbaren Tabellen, sodass durch Entfernen freigewordene Nummern erneut vergeben werden.
- **JOIN-Dialog: feste (fixe) Zusatzbedingungen in der ON-Klausel:** Über den neuen Button **„+ Add fixed condition"** lassen sich pro Join beliebige feste Bedingungen zur ON-Klausel hinzufügen, z. B. `CURRENT_TIMESTAMP BETWEEN t.valid_from AND t.valid_to` oder `t.type = 'TGB'`. Jede Bedingung wird komfortabel aus drei Teilen zusammengesetzt: linker Operand, Operator und rechter Operand. Operanden lassen sich entweder per Dropdown als **Spalte** (qualifiziert über den Tabellen-Alias) auswählen oder als **freier Wert/Ausdruck** eingeben (z. B. ein String-Literal `'TGB'` oder ein SQL-Ausdruck wie `CURRENT_TIMESTAMP`). Als Operatoren stehen `=`, `<>`, `<`, `<=`, `>`, `>=`, `LIKE`, `ILIKE`, `BETWEEN` (zwei rechte Operanden, mit `AND` verbunden) sowie `IS NULL`/`IS NOT NULL` (ohne rechten Operanden) zur Verfügung. Die festen Bedingungen werden in der Vorschau und im erzeugten Statement an die übrigen ON-Bedingungen mit `AND` angehängt und bleiben beim Umsortieren der Tabellen erhalten.
- **JOIN-Dialog: automatisch eingefügte Custom-Mapping-Bedingungen bearbeitbar:** Die aus benutzerdefinierten Spalten-Verknüpfungen (Custom Mappings) automatisch vorbelegten Zusatzbedingungen, die bisher nur schreibgeschützt angezeigt wurden, lassen sich jetzt über einen **„Edit"**-Button in eine editierbare feste Bedingung umwandeln. Dabei wird die Bedingung in den neuen Bedingungs-Editor (linker Operand / Operator / rechter Operand) überführt: Die Spalte bleibt als alias-qualifizierte Spaltenauswahl erhalten, der Wert wird als frei editierbares Literal übernommen. Anschließend können Operator und Operanden beliebig angepasst werden; die ursprüngliche schreibgeschützte Zeile wird dabei entfernt, sodass die Bedingung nicht doppelt erscheint.

Das Diagnose-Log zeigt jetzt den rohen `search_path`-String und den aufgelösten Benutzer.

Geloggt werden u. a. der beim Verbinden ermittelte Server-`search_path` (`SHOW search_path`), die Verbindungsdaten (Host/aufgelöste IP, Port, Datenbank, Benutzer, Anzeige-Schemas), sowie pro geöffneter Tabelle der zur Laufzeit abgefragte `search_path` (`current_schemas(false)`) und die daraus abgeleitete Tabellen-Referenz inkl. Begründung (ob/warum mit Schema qualifiziert wird). Das erleichtert die Diagnose von Fällen, in denen eine Tabelle aus dem falschen Schema geöffnet wird.

Bisher wurde die in der Verbindung hinterlegte Schema-Liste (ein reiner Anzeige-Filter) fälschlich als `search_path` interpretiert. Dadurch wurde z. B. eine Foreign Table aus `leda_dev` ohne Schema-Präfix abgefragt und die gleichnamige lokale Tabelle aus dem `search_path`-Schema (`leda`) geöffnet. - **Foreign Tables erscheinen jetzt in der Tabellen-Baumansicht:** Fremd-Tabellen (Foreign Tables, z. B. über `postgres_fdw` eingebundene Tabellen) wurden in der Baumansicht, der Tabellen-Suche, dem JOIN-Dialog und der Typeahead-Auswahl nicht angezeigt, wenn der PostgreSQL-Server sie in `information_schema.tables` als `'FOREIGN TABLE'` meldet (Server-Versionen < 9.5). Die Filter berücksichtigen jetzt beide Schreibweisen (`'FOREIGN'` und `'FOREIGN TABLE'`) über eine gemeinsame Konstante, sodass Foreign Tables versionsunabhängig wie normale Tabellen aufgelistet werden.
- **Verbindung bearbeiten ohne Passwort-Eingabe:** Beim Bearbeiten einer bestehenden Verbindung (z. B. um nur den Port, Host oder die Datenbank anzupassen) muss das Passwortfeld nicht mehr erneut ausgefüllt werden. Bleibt das Feld leer, wird automatisch das zuvor gespeicherte Passwort dieser Verbindung weiterverwendet, statt es mit einem leeren Wert zu überschreiben. Wird ein neues Passwort eingegeben, ersetzt dieses wie gewohnt das alte. Bei neuen Verbindungen bleibt das Verhalten unverändert.

Eine zuvor entfernte Tabelle kann über „+ Add tables…" wieder hinzugefügt werden.
- Im **JOIN-Dialog** werden die Join-Bedingungen jetzt zusätzlich aus **benutzerdefinierten Spalten-Verknüpfungen (Custom Mappings)** vorbelegt — nicht mehr nur aus Datenbank-Fremdschlüsseln. Existiert zwischen zwei am Join beteiligten Tabellen ein Custom Mapping `A.spalte → B.spalte`, wird daraus automatisch eine Join-Bedingung abgeleitet (für die anfänglichen Tabellen wie auch für nachträglich hinzugefügte). Doppelte Bedingungen (bereits über einen Fremdschlüssel abgedeckt) werden vermieden.
- Im **JOIN-Dialog** werden jetzt auch die im Custom Mapping hinterlegten **Zusatzbedingungen** in die ON-Klausel übernommen. Hat ein Mapping neben der Spalten-Verknüpfung weitere Bedingungen (z. B. `status = 'active'`), werden diese als literale Bedingungen an die jeweilige Join-Bedingung angehängt (z. B. `... ON b.id = a.b_id AND a.status = 'active'`). Die Werte werden korrekt als Zahl bzw. als gequotetes String-Literal formatiert. Die abgeleiteten Zusatzbedingungen werden im Dialog angezeigt, bleiben beim Umsortieren erhalten und lassen sich bei Bedarf einzeln entfernen.
- Der **JOIN-Dialog** lässt sich jetzt auch beim Ziehen einer **einzelnen Tabelle** öffnen: Wählt man beim Ablegen die Option **„Join"**, öffnet sich der interaktive JOIN-Builder mit dieser Tabelle als FROM-Tabelle. Über „+ Add tables…" lassen sich anschließend weitere Tabellen hinzufügen und die Join-Bedingungen konfigurieren (zuvor wurde nur ein statischer `JOIN … ON …`-Schnipsel eingefügt).
- **JSONB-/JSON-Werte sind in der Datenansicht jetzt sichtbar:** Spalten vom Typ `json`/`jsonb` werden vom Postgres-Treiber als JavaScript-Objekte/Arrays geliefert und wurden bisher als `[object Object]` angezeigt. Sie werden nun als formatierter JSON-Text dargestellt — sowohl in der Tabellenzelle als auch im Datensatz-Dialog („View full record") und in duplizierten Zeilen. Die Anzeige ist konsistent mit der Änderungserkennung, sodass unveränderte JSON-Zellen nicht mehr fälschlich als bearbeitet markiert werden.
- **„View Data" für SELECTs in Prozeduren/Funktionen:** In einer SQL-Datei (z. B. einem Schema-Skript mit vielen Prozeduren und Funktionen) gibt es jetzt im Editor-Kontextmenü den Eintrag **„View Data"**. Beim Rechtsklick innerhalb einer `SELECT`-Anweisung werden deren Anfang und Ende automatisch erkannt (per Semikolon-Grenzen, wobei Kommentare sowie String- und Dollar-Quoted-Literale ignoriert werden); ein eventuell vorhandener Prefix wie `RETURN QUERY` wird auf das `SELECT`/`WITH` zurückgeschnitten. Hat man stattdessen einen **Sub-Select oder eine WITH-Klausel markiert**, wird nur die Markierung verwendet und nicht auf die gesamte Anweisung erweitert. Die `INTO`-Klausel (auch `INTO STRICT`) wird automatisch entfernt, damit die Anweisung eigenständig lauffähig ist.
- **Variablen-Abfrage per Modal mit Cache:** Werden in dem erkannten SELECT Variablen verwendet (Werte in Vergleichen/`IN`/`LIKE`/`BETWEEN`-Listen, Positionsparameter `$1` sowie `user`/`current_user`/`session_user`/`current_role`/`current_catalog`), öffnet sich ein **modaler Dialog**, in dem für jede Variable optional ein Wert angegeben werden kann. Leere Felder lassen den Bezeichner unverändert; Werte werden 1:1 eingesetzt (String-Literale also inklusive Anführungszeichen). Die zuletzt verwendeten Werte werden **pro Variablenname zwischengespeichert** und beim nächsten Mal vorausgefüllt. Anschließend wird das Ergebnis in der **bestehenden Datenansicht in einem geteilten Editor (Split-View)** im schreibgeschützten Modus angezeigt.
- **Kopieren von Zahlen ohne Tausendertrennzeichen:** Beim Kopieren aus der Datenansicht werden bei numerischen Spalten die Tausendertrennzeichen (standardmäßig Leerzeichen) entfernt — aus angezeigt `9 999 999,99` wird in der Zwischenablage `9999999,99`. Das Dezimaltrennzeichen bleibt unverändert. Bei Mehrfachauswahl über mehrere Zellen werden die Zellen tab-/zeilengetrennt kopiert, wobei nur numerische Spalten normalisiert und Textspalten unverändert übernommen werden; Auswahlen ohne numerische Zellen verhalten sich wie das normale Kopieren.
- **Mehrzeiliger, formatierter SELECT in der Datenansicht:** Die Abfragezeile der Datenansicht ist jetzt ein **mehrzeiliges Eingabefeld** und zeigt den SELECT **standardmäßig formatiert** an: Jede Top-Level-Spalte steht eingerückt in einer eigenen Zeile, die Klauseln `FROM`/`JOIN`/`WHERE`/`GROUP BY`/`ORDER BY`/`LIMIT` usw. beginnen jeweils auf einer neuen Zeile und `WHERE`-Bedingungen werden an Top-Level-`AND` umgebrochen. Die Formatierung greift automatisch beim Öffnen der Tabelle, beim Auswählen aus dem Abfrageverlauf sowie bei Filter-, Ausschluss- und Sortier-Aktionen; ein neuer **„Format"**-Button formatiert auch manuell eingegebenes SQL. Innerhalb des Felds fügt **Enter** einen Zeilenumbruch ein, **Strg/Cmd+Enter** führt die Abfrage aus. Zeichenketten, Klammern, Funktionsaufrufe und Kommentare werden dabei korrekt behandelt; Anweisungen mit Kommentaren, CTEs (`WITH`) oder Nicht-`SELECT`-Statements bleiben unverändert.


## 1.0.0

- **Tabelle per Drag & Drop in den Editor ziehen:** Eine Tabelle aus der Tabellen-Baumansicht lässt sich jetzt direkt in einen beliebigen Texteditor ziehen. Beim Ablegen erscheint eine Auswahl mit **Name only**, **Insert**, **Delete**, **Update**, **Select** (Standard) und **Join**; während des Navigierens wird eine Live-Vorschau des erzeugten Statements angezeigt. Nach Bestätigung wird das Statement an der Cursor-Position eingefügt. Alle Statements enthalten sämtliche Spalten der Tabelle und qualifizieren die Spalten mit einem Tabellen-Alias (z. B. `SELECT lei.lei_id ... FROM leistungen lei`). Der Alias wird aus dem Teil des ersten Spaltennamens vor dem ersten Unterstrich abgeleitet (`lei_id` → `lei`) bzw. fällt auf den Tabellennamen zurück. Über einen Stift-Button in der Auswahl lässt sich der Alias pro Tabelle ändern; die Wahl wird gespeichert und beim nächsten Mal wiederverwendet.
- **Formatierter SELECT:** Der generierte SELECT listet jede Spalte eingerückt in einer eigenen Zeile auf (`SELECT`-Schlüsselwort und `FROM`-Klausel auf separaten Zeilen).
- **DELETE mit allen Spalten in der WHERE-Klausel:** Das per Drag & Drop erzeugte DELETE-Statement listet alle Spalten der Tabelle (qualifiziert) in der WHERE-Klausel auf, jeweils mit `AND` verknüpft.
- **UPDATE mit Typ-Cast:** Das per Drag & Drop erzeugte UPDATE-Statement setzt alle Spalten und castet jeden Wert auf den jeweiligen Spaltentyp (z. B. `amount = NULL::numeric`).
- **INSERT mit Typ-Cast:** Das per Drag & Drop erzeugte INSERT-Statement castet ebenfalls jeden Wert auf den jeweiligen Spaltentyp (z. B. `NULL::numeric -- amount`).
- **Mehrere Tabellen als JOIN SELECT einfügen:** Mehrere Tabellen lassen sich (mit `Strg`/`Shift`-Mehrfachauswahl) gemeinsam aus der Baumansicht in einen Editor ziehen. Es öffnet sich ein Bestätigungsdialog, der ein `SELECT … FROM … JOIN …` über alle Tabellen mit Live-Vorschau anzeigt. Die Join-Bedingungen werden automatisch aus vorhandenen Primär-/Fremdschlüsseln zwischen den Tabellen vorbelegt (Tabellen ohne Beziehung fallen auf `CROSS JOIN` zurück). Im Dialog lassen sich die Reihenfolge der Tabellen ändern, Aliase umbenennen, der Join-Typ (INNER/LEFT/RIGHT/FULL/CROSS) wählen sowie Join-Bedingungen hinzufügen, entfernen und bearbeiten. Nach Bestätigung wird das fertige Statement an der Cursor-Position eingefügt.
